## What was proven (recap, for the record)

engine were already proven; this increment proves the control-plane glue (ADR-0012 §2).

## Findings

### [FIX-1] zap logger — SOUND
`cmd/dagmar-controller/main.go`. controller-runtime v0.24 requires an explicit
`ctrl.SetLogger` or it drops all logs and spams a `priorityqueue` stack trace at boot (a real
v0.24 behaviour, accurately documented in the added comment). The fix is the Kubebuilder idiom:
`zapOpts.BindFlags` + `ctrl.SetLogger(zap.New(zap.UseFlagOptions(&zapOpts)))`. `go.mod` correctly
adds `go.uber.org/zap`, `go.uber.org/multierr`, and `github.com/go-logr/zapr` as indirect. No
defect. This does not violate ADR-0012 §3 leanness (it is required plumbing, not new machinery).

### [FIX-2] GitHub-release install vs `dl.dagger.io | sh` — SOUND, two latent notes
`run_controller.go:221-226`. The `dl.dagger.io | sh` install script 403s from inside some pod
networks (accurate); downloading the release tarball directly from `github.com` is a sound
workaround and `tar xz -C /usr/local/bin dagger` is correct. Two latent notes:
- **(a) `_linux_amd64` is hardcoded.** Breaks on arm64 nodes (e.g. Apple-Silicon docker-desktop).
  The smoke ran on amd64 (WSL2), so it passed. Portability latent defect — phase-1 productionized
  image should detect arch or use `dl.dagger.io`'s arch-aware path.
- **(b) no checksum/signature verification** of the downloaded binary (TOFU / supply-chain).
  Acceptable for Phase-0 dev over HTTPS; pin + verify the release checksum for production.

### [FIX-3] `deploy-engine` as a prerequisite (not reconciled) — SOUND
`Justfile`. Correctly frames the singleton engine as a *manual prerequisite* (`PREREQUISITE for
Runs — engine management is NOT reconciled by the Phase-0 controller; ADR-0012 §2`), matching
ADR-0012 §2 (engine management is out of Phase-0 controller scope) and ADR-0008 (singleton engine
is a substrate concern). The cbb8 helm recipe (`oci://registry.dagger.io/dagger-helm`,
`image.tag=v0.21.8`, `privileged=true`, ns `dagmar`) matches the spike. Minor coupling:
`kubectl rollout status daemonset/dagger-dagger-helm-engine` and the reconciler's
`engineLabelVal` both hardcode the helm chart's daemonset name/label — if the chart renames it,
both break silently. Note only.

### [FIX-4] `moduleRef` load-bearing — SOUND
`project.yaml` + `run_controller.go`. Wires `project.Spec.ModuleRef` into `dagger call -m`,
defaults to `github.com/denkhaus/dagmar` (dogfood: dagmar calls its own published self), and is
validated as a terminal config error when empty (reconciler step 3 + dedicated test). Closes
ADR-0012 §2 GAP-1 read #2 and review 12's blocker (a). The `project.yaml` comment correctly
cites the ADR anchor. No defect.

### [GAP-1] Shell-injection surface is under-documented (not a Phase-0 defect)
`run_controller.go:221-226, 293-297`. The `sh -c` command interpolates **three** unescaped,
unquoted author fields: `ModuleRef` (Project CR), `ModuleFunction` (Run CR), and `ModuleArgs`
(Run CR, via `shellJoin`). The `shellJoin` comment only calls out `ModuleArgs` as
"author-controlled via the Run CR, a privileged resource … Revisit for Phase 2 untrusted input."
The *reasoning* is sound for Phase 0 — all three are privileged-author fields (creating a Run or
Project requires RBAC), and the Phase-2 revisit flag is correct. But the comment's scope is
**incomplete**: `ModuleRef` and `ModuleFunction` are equally injectable, and a value containing a
shell metacharacter (`;`, `$(…)`, backtick) or even a space would be interpolated raw. There is
also no test guarding well-formedness. Recommend: extend the comment to name all three
interpolation sites (not just `ModuleArgs`), and add a Phase-2 note that *agent-generated* Runs
would make this a live injection vector.

### [GAP-2] Multi-namespace RoleBinding binds only the FIRST namespace (latent; ADR-0008 §4)
`run_controller.go:139-183`. The engine-namespace RoleBinding `dagmar-agent-exec` is created once
with `Subjects = [{SA: dagmar-agent, Namespace: <first-run-ns>}]`; subsequent Runs in *other*
namespaces find it already existing and skip (no subject appended). Net effect: only the first
Project's namespace can `pods/exec` into the engine. Single-namespace Phase 0 never hits this,
but **ADR-0008 §4 mandates per-Project namespaces**, so the second Project silently loses engine
access. The doc-comment "Shared (created once per namespace), not per-Run" is also misleading —
the Role/RoleBinding are created once *globally* in the engine ns and bind a single namespace.
Belongs under `dagmar-67bc` (reconciliation/RBAC design): the seed tracks the Role/RoleBinding
*cleanup* and "module ref on kind vs production", but not this multi-subject *binding* defect.

### [GAP-3] Shared SA `ownerRef` cascades on Run deletion (latent; even single-namespace)
`run_controller.go:144-156`. The per-namespace SA `dagmar-agent` is shared across all Runs in a
namespace but receives `ctrl.SetControllerReference(run, sa, …)` to the *first* Run that created
it. Deleting that Run garbage-collects the SA (controller-runtime GC follows the ownerRef),
breaking every other Run in the namespace — reachable within Phase 0 if two Runs coexist. The
engine-ns Role/RoleBinding *leak* (no ownerRef possible cross-namespace) is acknowledged and
tracked in `dagmar-67bc`; the SA *over-ownership* is not. Both are `dagmar-67bc`
reconciliation/finalizer-model concerns (ADR-0012 §2 defers finalizers/cleanup).

### [GAP-4] Runtime CLI install on every Run (no baked image) — known, deferred
`run_controller.go:217-226`. Each Run spawns a fresh `alpine:3.20` pod that runs
`apk add kubectl curl` and downloads the ~100 MB dagger tarball from `github.com` before doing
any work: slow cold-start, network-dependent (github.com availability), non-reproducible. This is
a *deliberate* Phase-0 choice matching the cbb8 Probe recipe (the code comment says so). A baked
`dagmar-agent` image (dagger + kubectl pre-installed) is the natural Phase-1 productionization
path (ADR-0012 §4 CI / "productionization alongside"). Track as a Phase-1 item, not a Phase-0
defect — but the per-Run download cost will bite CI throughput once Runs are frequent.

### [GAP-5] Private-module engine-auth path is UNRECORDED (Phase-2 credential concern)
The engine fetches the module server-side from the git ref (`dagger call -m github.com/…`); the
engine is unauthenticated, so `github.com/denkhaus/dagmar` had to be flipped **public** for the
smoke. This is correctly **not** a Phase-0 defect (the dogfood module is public). But the auth
path is not a clean fit for ADR-0007's `vcs` class: `vcs` projects Workspace clone/push
credentials into the *Sandbox pod's* `dag.Env()` (ADR-0007 §5), whereas an engine-side fetch of a
*private module ref* needs *engine-level* git credentials (or an authenticated module mirror) —
a distinct mechanism. A repo-wide grep finds this recorded **nowhere** (not in CONTEXT.md,
ADR-0007, ADR-0012, or `.seeds/`). Recommend recording it now — under `dagmar-67bc` scope item 4
("how the agent pod points at the right module ref on kind vs production") or as a Phase-2 note
on ADR-0007 — so it is not rediscovered painfully when a private module is first needed.

### [HOUSE-1] docker-desktop substrate deviation leaves ADR-0012 §1 stale
ADR-0012 §1 / §5 and the CONTEXT.md ADR-0012 summary all say "kind substrate." Increment 2 was
empirically proven on **docker-desktop** (chosen for k9s inspection; the dispatch path is
substrate-agnostic, so this does not invalidate the kind *decision*). The Justfile `deploy`
comment now says "kind/docker-desktop," but the ADR/CONTEXT do not record the docker-desktop
proof. Recommend a one-line note in ADR-0012 §1 recording docker-desktop as a proven-equivalent
dev substrate and reaffirming the substrate-agnosticism of the dispatch vertical, so the record
matches reality and the §5 Phase-0 "on kind" line is not read as a proof claim that wasn't met.

### [HOUSE-2] `kind load … 2>/dev/null || true` masks real failures
`Justfile deploy`. Making the kind image-load optional is necessary (docker-desktop has no kind),
but `2>/dev/null || true` swallows *all* errors — on a real kind cluster, a genuine load failure
(wrong image name, daemon down) is silently masked and the deploy then fails opaquely at image
pull. Prefer detecting the cluster type (`kubectl config current-context`) and loading
conditionally, rather than blanket-suppressing.

### [HOUSE-3] Status `reason` for a failed pod is "Reconciling"
`run_controller.go:118-120, 252-260`. When the agent pod reaches `PodFailed`, `setStatus` mirrors
`Phase=Failed` but with `Reason="Reconciling"` / `Message="agent pod observed"` — misleading for
a terminal failure (contrast `failRun`'s specific reasons, e.g. `ProjectNotFound`,
`ModuleRefRequired`). Minor; the full status-condition vocabulary is deferred to `dagmar-67bc`.
A cheap improvement: a distinct reason (`AgentPodFailed`) on the failure-mirror path.

### [HOUSE-4] Empty `ModuleFunction` is not validated (asymmetric with `ModuleRef`)
`run_controller.go`. Empty `ModuleRef` → terminal `failRun` (tested). Empty `ModuleFunction` → no
validation; the pod runs `dagger call -m <ref>  <args>` (no function) and fails at runtime →
`Run=Failed` via phase mirror. The handling is asymmetric. Minor — either validate
`ModuleFunction` like `ModuleRef`, or document that runtime-failure mirroring is the intended
catch-all for malformed call shapes.

### [SPEC-1] Coherence with ADR-0008 §2 (`kube-pod://` + SA + `pods/exec`) — CONFIRMED
Runner host `kube-pod://<enginePod>?namespace=dagmar`, `_EXPERIMENTAL_DAGGER_RUNNER_HOST` env,
per-namespace SA, engine-ns Role (`pods`/`pods/exec`) + RoleBinding binding that SA — all match
ADR-0008 §2 and the cbb8 spike (mulch `mx-e0cba3`). ✓ (Subject to [GAP-2]/[GAP-3] when scaling to
multiple Projects/namespaces.)

### [SPEC-2] Least-privilege over-grant in the agent Role
`run_controller.go:161-163`. The engine-ns Role is
`Resources: ["pods","pods/exec"], Verbs: ["create","get"]` — the cartesian product grants
`create` on `pods` (not only `pods/exec`), letting the agent SA *create arbitrary pods* in the
engine namespace. For `kube-pod://`, only `pods/exec: create` (+ `pods: get` to resolve the
engine pod) is required. Recommend two separate rules: `{Resources:["pods"], Verbs:["get"]}` and
`{Resources:["pods/exec"], Verbs:["create"]}`. Aligns with the ADR-0007/0008 least-privilege
spirit (blast-radius minimisation).

### [SPEC-3] Coherence with ADR-0012 §2 (Phase-0 reads) — CONFIRMED
agent-pod image (`Project.AgentPodImage`, default `alpine:3.20`) ✓; module ref
(`Project.ModuleRef`, load-bearing, validated) ✓; status conditions + phase mirrored from the
owned pod ✓. The deferred items (requeue/backoff/finalizers, ProjectManifest, os-eco binding,
full reconciliation semantics) remain correctly deferred to `dagmar-67bc` / Phase 2. The
dispatch vertical delivers exactly the §2 bootstrap boundary.

### [SPEC-4] Coherence with ADR-0012 §3 (lean controller-runtime) — CONFIRMED
`main.go`: no leader-election, no webhook server, no conversion; `healthz`/`readyz` registered;
`Owns(&corev1.Pod{})` wires pod-phase changes to re-enqueue the owning Run (so the status mirror
fires without an explicit requeue). The added zap logger is required v0.24 plumbing, not new
machinery — leanness preserved. ✓
