## A. Standards

The ADR is well-structured and self-consistent internally. Its decision sections are clear,
alternatives are thorough, and the "everything is Dagger code" paradigm is a coherent
simplification. The following standards-level issues arise from cross-document coherence, not
from the ADR's internal logic.

**[FIX] A1 — `dagmar-gate = what AND how` reverses review-11 GAP-3 without front-and-center
reconciliation.** ADR-0012 §4 (L181–183) explicitly rejected the framing "`dagmar-gate` IS the
checkable" — *"it would make the manifest `checkables:` section a second source and break
ADR-0009 §2's two-layer model."* ADR-0017 §3 now adopts exactly that framing. The ADR's
Consequences note this indirectly ("dagmar-gate = what AND how") but do not acknowledge that a
previously *explicitly rejected* position is now the decided one. The rejection's rationale
("second source") is indeed mooted by removing the manifest section entirely — but that argument
should be stated explicitly, not left for the reader to infer. The review-11 GAP-3 decision was
load-bearing; reversing it deserves a named supersession, not an implicit one.

**[FIX] A2 — Tier-A `checkable` term now overloaded (naming discipline).** CONTEXT.md defines
`checkable` as a **Tier-A Dagger** concept (`CodeWorkspace(source, checkable)`) *and* ties it to
manifest-declared content. ADR-0017 removes the manifest-declared half but keeps the term. Post-0017,
"checkable" means both (a) Dagger's `CodeWorkspace` checkable parameter (Tier A, unchanged) and
(b) "the logic inside `dagmar-gate`" (now code, no separate data). The ADR uses "checkable"
throughout without disambiguating which sense applies. CONTEXT.md's `checkable` glossary entry
needs splitting or sharpening.

Fowler smells: no significant code smells (no code changed). The ADR itself shows mild
**Speculative Generality** in §5 ("it may carry future manifest metadata types") and §4 ("may
persist as a thin metadata file, or be absorbed entirely into module function parameters") —
both hedge on undecided futures without committing.

## B. Spec

**[SPEC] B1 — Spike `dagmar-e8f3` scope exceeded.** The seed's title: *"Spike: os-eco
tool-wrapping — manifest-declared bash commands as LLM tools (data-driven tool-registration
feasibility)."* The spike's load-bearing question (ADR-0013 §5 L188–193) was: *can the Dagger
LLM primitive expose a data-driven tool-registration surface?* ADR-0017 answers this but then
extends to a much broader redesign — unifying ALL project hooks and superseding manifest
checkables. The os-eco question (LLM tools) and the checkables question (gate logic) are
distinct concerns that the ADR conflates under one decision. The pivot is acknowledged ("the
answer surfaced the deeper question") but the ADR should separate the two: (1) os-eco wrapping
= code (answers the spike), (2) checkables also = code (a separate, broader decision that
deserves its own justification).

**[SPEC] B2 — ADR-0013 §5 D12 (os-eco bindings) is directly replaced but not mentioned.**
ADR-0013 §5 (L182–222) specifies the os-eco binding mechanism in detail: manifest-declared bash
commands → dagmar wraps → **LLM tools** (`issues_read`, `issues_write`, etc.), with five
hermeticity rules and a feasibility gate on the spike. ADR-0017 replaces this entire mechanism
(named Dagger functions instead of manifest bash commands). Yet ADR-0013 is **absent** from
ADR-0017's Consequences supersession list (which covers ADR-0003, 0009 §2, 0012 §4, 0014 only).
This is a spec-level omission — the most detailed existing specification of the os-eco surface
is silently invalidated.

## C. Inconsistencies / contradictions

**[FIX] C1 — CONTEXT.md `checkable` glossary contradicts ADR-0017 §3.** The entry reads:
*"declared per-project in the ProjectManifest (`checkables:`, ADR-0003) and run by the
always-Dagger wrapper function `dagmar-gate`."* ADR-0017 §3 supersedes the manifest `checkables:`
section — checkables are now code inside `dagmar-gate`, not manifest-declared data.

**[FIX] C2 — CONTEXT.md `ProjectManifest` entry contradicts ADR-0017 §3/§4.** The entry
specifies: *"manifest declares **what** the checkables are; the Dagger function `dagmar-gate` …
is the **execution wrapper** … manifest = what, dagmar-gate = how."* ADR-0017 explicitly replaces
this with "dagmar-gate = what AND how" and says the manifest "carries only metadata if it carries
anything at all."

**[FIX] C3 — CONTEXT.md `Project` CRD entry is stale.** *"Project-specific content (incl.
`checkables`) lives in the manifest, not on the CR."* — with `checkables:` superseded, this is
no longer accurate.

**[FIX] C4 — `.dagmar/project.yaml` comment block is stale (intentionally).** The file's header
reads: *"manifest = what, dagmar-gate = how"* and describes checkables as manifest-declared. This
is the **live conformance contract** — it currently works as-is (ADR-0017 defers code changes to
Phase 2). The ADR should note that these in-code comments are intentionally stale until the Phase 2
refactor, so a reader doesn't assume the code contradicts the ADR by accident.

## D. Undefined / under-defined terms

**[GAP] D1 — "Project Hook" and "os-eco hook" are new terms absent from CONTEXT.md glossary.**
ADR-0017 introduces "Project Hook" as the central concept but it appears in no glossary. It
overlaps with existing terms: `dagmar-bootstrap`/`dagmar-gate` were called "gate-family" or
"Dagger functions"; `dagmar-issues`/`dagmar-memory`/`dagmar-prompt` overlap with the Tier-B
adapter-port terms (`IssueTracker`, `Memory`, `Prompts`). The relationship between "hooks" and
"ports" is undefined (see E1).

**[GAP] D2 — os-eco hook signatures are materially underspecified.** §2's registry table gives
function names and purposes but **no contract**: no input parameters (does `dagmar-issues` take a
`*dagger.Directory`? a query string? a typed struct?), no return types, no error contract, no
idempotency expectations, no concurrency model. Since ADR-0017's entire thesis is "the function
signature IS the contract" (replacing the manifest schema), leaving signatures unspecified means
the contract is undefined. For comparison, `dagmar-bootstrap`/`dagmar-gate` have explicit
signatures in `.dagmar/main.go` (`ctx, *dagger.Directory, *dagger.Secret → (string, error)`). The
os-eco hooks need the same level of specification, or at minimum a commitment to define them
before Phase 2.

**[GAP] D3 — "degrades gracefully" is undefined behavior.** §2: *"When present, dagmar uses
them; when absent, dagmar degrades gracefully."* What does this mean concretely? Does the agent's
`Env` omit the issue-tracking tool entirely? Does dagmar probe for function existence at dispatch
time (and how — by module introspection? by convention-only?). ADR-0014 §4 says a runtime
conformance probe is "later hardening" — but the optional-hook model fundamentally requires a
detection mechanism, unlike the required `dagmar-bootstrap`/`dagmar-gate`.

**[GAP] D4 — Hook caller is ambiguous (LLM tool vs infrastructure hook).** §6 implies os-eco
hooks run *inside the hermetic loop* ("No network within the hermetic loop"). But §2 says only
"dagmar uses them." ADR-0013 §5 specified these as **LLM tools on the `Env`** (the agent calls
`issues_read` during its loop). Are `dagmar-issues`/`dagmar-memory`/`dagmar-prompt` registered as
LLM tools on the agent's `Env`? Or are they infrastructure hooks dagmar's controller calls? The
distinction is architecturally critical: LLM tools need Dagger's tool-registration surface;
infrastructure hooks need a dispatch path. The ADR must state which.

## E. Referenced-but-missing ADRs / undecided decisions

**[GAP] E1 — Hook-vs-port relationship with ADR-0001 Tier B and ADR-0005 is undecided.**
CONTEXT.md's Tier-B entries (`IssueTracker → seeds`, `Memory → mulch`, `Prompts → canopy`)
describe **adapter ports** consumed behind dagmar's hexagonal boundary. ADR-0017's
`dagmar-issues`/`dagmar-memory`/`dagmar-prompt` are **project module functions**. Are the ports
now implemented by calling the project's hooks? Does the adapter-port model survive, or do hooks
replace ports? §7 says "os-eco CLI names appear only inside the Project's hook implementations" —
implying the port abstraction moves INTO the project module (the project implements the adapter).
But this reverses ADR-0001's Tier-B model (dagmar owns the adapter; os-eco names appear only in
dagmar's adapter code). No ADR reconciles this. Additionally, `dagmar-prompt` vs ADR-0005's
specific cross-store merge mechanism (dagmar-side Go layer, `cn render` ×2 + merge) — does the
project's `dagmar-prompt` replace dagmar's merge, or wrap it?

**[GAP] E2 — ADR-0014 published-library reconciliation is unresolved.** ADR-0014's GAP-1
resolution (dagmar-a1e0, 2026-08-07 — **one day before ADR-0017**) established
`github.com/denkhaus/dagmar/manifest` as a published shared library specifically to carry
`ProjectManifest`/`Checkable`/`ParseManifest`/`validateWorkdir` — the gate's contract types.
ADR-0017 §5 deprecates exactly these types. The library's reason for existence evaporates. The
ADR says "it may carry future manifest metadata types" (speculative) but does not address: what
happens to the published library during the migration? Does it become a near-empty package? What
replaces it as the platform-authority contract for whatever metadata remains? If the manifest
shrinks to "thin metadata" (§4), should those metadata types be defined in the library now?

**[GAP] E3 — Hermeticity claim (§6) vs ADR-0011 residual.** §6: *"No network within the
hermetic loop."* But as named Dagger functions (like `dagmar-gate`), the os-eco hooks run via
container-exec, which has outbound network by default (ADR-0011 ProbeNet). ADR-0011 §2 defines
"hermetic" as a *tool-surface constraint, not a network air-gap*. §6's "no network" reads as a
stronger claim than ADR-0011's definition. Either (a) the hooks are hermetic in ADR-0011's
tool-surface sense (they don't *use* network, but the residual exists) — then §6 should say so;
or (b) a mechanism enforces file-ops-only — then it needs to be specified (how? Dagger has no
per-exec no-network flag per ADR-0011).

## F. Housekeeping

**[HOUSE] F1 — ADR-0003 has no superseded forward-pointer.** Status is still "decided"; the body
still asserts "`checkables` are **required** project-specific content in the manifest." ADR-0017
§3 supersedes this. ADR-0003 needs a forward-pointer to ADR-0017 (at minimum a note; ideally a
Status change to "partially superseded by ADR-0017").

**[HOUSE] F2 — ADR-0009 §2 has no forward-pointer.** §2 still reads "manifest = what, Dagger
function = how to invoke. `dagmar-gate` does not re-declare checkables." ADR-0017 replaces this.
(ADR-0009 §2 was already reassigned once by ADR-0012; a second supersession note is warranted.)

**[HOUSE] F3 — ADR-0012 §4 has no forward-pointer.** §4 contains the most extensive affirmation
of "manifest = what, dagmar-gate = how" (L88–91, L128–129, L207) and the review-11 GAP-3 rejection
(L181–183). All of this is now superseded by ADR-0017 §3. A forward-pointer is needed.

**[HOUSE] F4 — ADR-0011 §2 carve-out note references stale gate-body provenance.** The note says
"the gate **body** is **project-declared** (manifest, ADR-0003)." Post-0017, the gate body is
in-code, not manifest-declared. The security reasoning (gate body is reviewable, pinned ref) still
holds — the body is still project-scope and gate-reviewed — but the "(manifest, ADR-0003)"
reference is now inaccurate.

**[HOUSE] F5 — `.dagmar/main.go` and `gate.go` code comments reference the old model.**
`DagmarGate`'s doc comment says "manifest = what, dagmar-gate = how (review-11 GAP-3)." `gate.go`'s
comment says "runs the manifest-declared checkables." These are intentionally stale (code deferred
to Phase 2 per ADR-0017 Consequences) but should be noted as such — a reader landing in the code
today sees a model that contradicts the latest ADR.

## Suggested next ADRs (priority order)

1. **ADR-0018: os-eco hook contract** — specify `dagmar-issues`/`dagmar-memory`/`dagmar-prompt`
   signatures (inputs, outputs, error contract), the caller model (LLM tool vs infrastructure
   hook), the optional-hook detection mechanism, and the hook-vs-port relationship (Tier-B adapter
   model). This is the highest priority: ADR-0017's thesis ("signature IS the contract") is hollow
   without signatures.

2. **ADR-0013 §5 D12 supersession** — explicitly record that the manifest-declared bash-command
   tool mechanism (five hermeticity rules, `issues_read`/`issues_write` tool names, feasibility
   gate) is replaced by ADR-0017's named-function approach. Update or annotate ADR-0013 §5.

3. **ADR-0014/manifest-library fate** — decide what happens to the published `manifest/` library
   when its primary types are deprecated. Does it carry metadata types? Does it shrink? Is the
   library still worth the cross-module published-dependency cost for metadata alone?
