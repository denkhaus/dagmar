## A. Standards

The four ADRs form a coherent Phase-2 design arc. ADR-0018's port-layer removal is a sound simplification: three Go interfaces, their adapters, binding types, and mocks were speculative scaffolding that Dagger's own module/introspection system now provides. The Tracer/Span survival is well-justified (observability is a different concern than Project Hooks). ADR-0019's two-tier conformance model (name-presence now, parameter checking in Phase 3) is pragmatic. ADR-0020's ephemeral-directory + branch-based lineage is simpler than volume management. ADR-0021's single-Loop-per-Run with controller orchestration for multi-step is the right separation.

Fowler smells: the code changes are deletions (removing dead code), so no new smells are introduced. The ADRs show **Speculative Generality** in ADR-0019's "Phase 3 deferred" parameter checking — but this is correctly scoped as future work, not gratuitous. ADR-0021's code sketches (`Code`, `app.Code`) are design-stage and should be treated as pseudocode; however, they are presented as compilable Go, which creates the API-accuracy findings below.

**Build gate:** `.dagger` module — `go build`/`go vet`/`go test` all green. The deleted `mock_oseco.go` (209 lines) is replaced by `mock_tracer.go` (92 lines); `generate.go` and `tools.go` updated to match.

**[FIX] A1 — `MaxAPACalls` typo in CONTEXT.md L227.** The CRD bridge table reads:

> `| maxAPICalls | LLMOpts{MaxAPACalls} (ADR-0021 D4) |`

The field is `MaxAPICalls` (with `I`), not `MaxAPACalls`. The generated SDK (`dagger.gen.go` L12762), ADR-0021 (throughout), and CONTEXT.md L59 all use `MaxAPICalls`. This is a one-character omission that would break compilation if copied.

**[FIX] A2 — `WithCurrentModule()` vs `WithMainModule()` contradiction between ADR-0019 and ADR-0021/CONTEXT.md.** This is the most important finding. Three documents disagree on which SDK method registers the project's LLM-Tool hooks:

- **ADR-0019 D2** (correct): "LLM-Tool hooks are registered via `Env.WithMainModule()`" — takes a `*Module` argument (the project module).
- **ADR-0021 D2** (code sketch): `env.WithCurrentModule()` — takes no argument; registers the **calling** module's functions.
- **ADR-0021 D7** (prose): "The `code` function's Env includes `WithCurrentModule()` (registers the LLM-Tool hooks)"
- **CONTEXT.md** Env entry (L42): `env.WithWorkspace(source).WithCurrentModule()`

The `Code` function lives in `.dagger/` (the platform module). `WithCurrentModule()` registers `.dagger/`'s own functions — it does **not** register the project's hooks (`dagmar-issues`/`dagmar-memory`/`dagmar-prompt` in `.dagmar/`). To register the project module's functions, `WithMainModule(projectModule)` is required. ADR-0019 correctly identifies this; ADR-0021 and CONTEXT.md do not.

**[FIX] A3 — `Module.Functions(ctx)` does not exist in v0.21.8 (ADR-0019 D4).** The conformance check code calls `funcs, err := mod.Functions(ctx)`, but `*Module` has no `Functions` method in the generated SDK. The available introspection paths are: `mod.Objects(ctx)` → `[]ObjectTypeDef` → each object's `Functions(ctx)` → `[]FunctionTypeDef`, or `mod.IntrospectionSchemaJSON(ctx)`. `*ObjectTypeDef` and `*InterfaceTypeDef` do have `Functions(ctx)`, but `*Module` does not. The conformance code as written will not compile.

**[FIX] A4 — `agent.TokenUsage()` stale reference in CONTEXT.md L64.** The TokenUsage glossary entry says `agent.TokenUsage()`, but ADR-0021 D4 and CONTEXT.md L62 both use `llm.TokenUsage()`. The SDK method is on `*LLM` (verified: `func (r *LLM) TokenUsage() *LLMTokenUsage`). There is no "agent" type with a `TokenUsage()` method. The reference appears to predate the LLM-centric API model.

**[FIX] A5 — ADR-0017 §8 describes a dead bridge model (L168–175).** §8 ("Hook-vs-port relationship") still presents the port-based bridge as live architecture:

> "The Tier-B adapter ports (`IssueTracker`, `Memory`, `Prompts` in `.dagger/internal/ports/`) are dagmar's **internal** domain interfaces… the adapter bridges port → project hook."

ADR-0018 D1 **deleted** those exact interfaces from `.dagger/internal/ports/`. The section has no annotation that the ports it describes are gone. A reader landing on §8 sees a fully specified port → adapter → hook pipeline that is architecturally dead. The asymmetry blockquote (L177–181) was added but the core paragraph (L168–175) was left intact. §8 needs a strikethrough or superseded-annotation matching the treatment ADR-0010 §3/§5 received.

**[FIX] A6 — CONTEXT.md Tier B entries and "Two paths to seeds" still name deleted Go interfaces.** The Tier B section (L76–86) lists `IssueTracker`, `Memory`, `Prompts` as glossary terms — these were the Go port interface names deleted in ADR-0018. The actual functions are `dagmar-issues`, `dagmar-memory`, `dagmar-prompt` (ADR-0019). Additionally, L172 ("A seeds / IssueTracker concept") and L207 ("agents use the IssueTracker adapter (CRUD issues)") reference the deleted `IssueTracker` port as if it still exists. Post-ADR-0018, agents call `dagmar-issues` as a native Dagger tool, not an adapter.

## B. Spec

The ADRs resolve their originating seeds cleanly:
- ADR-0018 ← seed dagmar-624c (closed) — port layer removal ✓

- ADR-0020 ← seed dagmar-e1f1 — workspace model ✓
- ADR-0021 ← seed dagmar-8d4a — loop-wrapping ✓

No spec drift. The ADRs build on each other in the right order (0017 → 0018 → 0019; 0020/0021 independent of 0018/0019 but reference them).

**[GAP] B1 — Post-Loop workspace harvest mechanism is undefined (ADR-0021 D8 vs ADR-0020 D3).** ADR-0021 D8 says "The controller harvests [the workspace mutation] for the PR flow" and lists: "1. Reads the modified workspace from the Run's pod (or the engine retains it)." ADR-0020 D3 says the controller "Extracts the Changeset from the completed Loop's workspace (`.AsPatch()` or `.After()`)." But the `Code` function returns `(string, error)` — a summary string. The K8s controller has no handle to the post-Loop `*dagger.Workspace` or `*Changeset` (these are Dagger SDK types, available only inside the module context). The phrase "or the engine retains it" is not a mechanism. The gap: either the `Code` function must return a `*dagger.Directory`/`*Changeset`/`*dagger.File` (patch) that the controller can then dispatch another function against, or there must be an explicit post-Loop function the controller calls. This is load-bearing for the PR flow (ADR-0020 D3 step 1) and should be resolved before Phase-2 implementation.

**[GAP] B2 — Where does `workspace.Update()` get called?** ADR-0020's API reconciliation and CONTEXT.md (L47) say "Post-Loop changes captured via `workspace.Update()` → `*Changeset`." The `Code` function sketch (ADR-0021 D1/D2) does not call `workspace.Update()` — it returns after `llm.Sync(ctx)`. If `workspace.Update()` is the controller's job (ADR-0020 D3 step 1), the controller needs a `*Workspace` reference — but `workspace` is constructed inside the `Code` function's Env and is not returned. This is the same mechanism gap as B1, viewed from the SDK-method side.

## D. Undefined / under-defined terms

**[GAP] D1 — "Changeset" used but not glossary-pinned.** ADR-0020 and ADR-0021 reference `*Changeset`, `.AsPatch()`, `.Before()`, `.After()`, `.DiffStats()` as established API concepts. CONTEXT.md mentions `workspace.Update()` → `*Changeset` inline but does not define "Changeset" as a Tier-A term. Since it is a Dagger SDK type (Tier A), it should either be added to the Tier-A glossary section or at minimum noted as a Tier-A reference (like `TokenUsage`).

**[GAP] D2 — "Sub-Run" vs "atomic Run" terminology (CONTEXT.md + ADR-0021 D3).** CONTEXT.md defines "atomic Run" and "orchestration Run" (ADR-0016). ADR-0021 D3 introduces "Sub-Runs" as a term for atomic Runs under an orchestration Run. CONTEXT.md's execution quartet section says "the quartet applies to atomic Runs and Sub-Runs" — using "Sub-Run" without a glossary pin. Is "Sub-Run" a synonym for "atomic Run under an orchestration Run"? The relationship should be explicit.

## E. Referenced-but-missing ADRs / undecided decisions

**[GAP] E1 — The post-Loop workspace → PR mechanism (B1/B2) likely needs an ADR or ADR-0021 amendment.** ADR-0020 D3 and ADR-0021 D8 both defer to "the controller harvests it" without specifying how the K8s controller obtains a Dagger SDK type handle to the post-Loop workspace. This is not a documentation gap — it's an undecided design point that blocks Phase-2 implementation. Options include: (a) `Code` returns `*dagger.Directory` (modified workspace) and a separate `Diff`/`PR` function handles extraction; (b) `Code` calls `workspace.Update()` internally and returns the patch; (c) the controller dispatches a follow-up function. Each has different implications for the controller ↔ module boundary.

No other referenced-but-missing ADRs. The ADR chain 0017 → 0018 → 0019 is complete; 0020/0021 reference 0017/0019 correctly.

## F. Housekeeping

**[HOUSE] F1 — ADR-0018 D2 references `adapters/otel/` as if implemented.** D2 says "The default implementation (`adapters/otel/`) wraps Dagger's built-in OpenTelemetry." The directory `.dagger/internal/adapters/otel/doc.go` exists (just a doc file, no implementation). The phrasing implies a working adapter that doesn't exist yet. Should say "will wrap" or note it's a placeholder.

**[HOUSE] F2 — ADR-0021 D8 code comment "Loop + Sync equivalent" is misleading.** The sketch calls `llm.Sync(ctx)` without a preceding `llm.Loop()`. The comment "Loop + Sync equivalent" suggests `Sync` replaces `Loop`, but in the lazy SDK, `Loop()` returns a new `*LLM` (the looped LLM) and `Sync(ctx)` forces evaluation. The correct pattern is `llm = llm.Loop()` then `llm, err = llm.Sync(ctx)`. The sketch omits the `.Loop()` call.

**[HOUSE] F3 — ADR-0021 D3 says "the quality-gate pipeline (ADR-0009)" but should reference ADR-0016.** D3's multi-step orchestration example uses the quality-gate pipeline as a case, referencing "ADR-0016 dual-mode Run" — correct for the orchestration mechanism. But the example itself ("Sub-Run 1: coder → Loop, Sub-Run 2: reviewer → Loop") describes the ADR-0009 quality-gate family. The reference is fine but could clarify that ADR-0016 provides the mechanism and ADR-0009 provides the specific pipeline instance. Minor — not a contradiction.

**[HOUSE] F4 — `skills-lock.json` is a new 155-line file with no ADR or CONTEXT.md mention.** It appears to be a Prime Agent skills lock file, unrelated to dagmar's architecture. It may be committed accidentally (infrastructure artifact). If intentional, it should be documented or `.gitignore`d.

## Suggested next ADRs (priority order)

1. **Amend ADR-0021 or create ADR-0022: post-Loop workspace → PR mechanism.** Resolve B1/B2/E1: how does the K8s controller obtain the post-Loop workspace state? Specify whether `Code` returns `*dagger.Directory`/`*Changeset`/patch, or whether a separate post-Loop function is dispatched. This is the highest-priority gap — it blocks the entire PR flow (ADR-0020 D3).

2. **Reconcile ADR-0021/CONTEXT.md with ADR-0019 on `WithCurrentModule()` vs `WithMainModule()` (A2).** This is not a new ADR — it's a fix to ADR-0021 D2/D7 and CONTEXT.md to use `WithMainModule(projectModule)` (correct per ADR-0019 and the SDK). Decide whether both `WithCurrentModule()` (for `.dagger/` platform tools) and `WithMainModule(projectModule)` (for LLM-Tool hooks) are needed, or only the latter.

3. **ADR-0019 D4 conformance code correction (A3).** Update `Module.Functions(ctx)` to the actual introspection path (`Module.Objects(ctx)` → `ObjectTypeDef.Functions(ctx)`, or `Module.IntrospectionSchemaJSON(ctx)`). Not a new ADR — a correction to the existing code example.
