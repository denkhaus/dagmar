## 2. Findings

### [FOUNDATIONS-1] `GOPRIVATE` is framed as load-bearing in the resolution recipe but is wired nowhere — and is in fact unneeded for the public repo — GAP

**Severity:** medium (accuracy of the increment's central engineering claim). **Files:**
`manifest/doc.go:15–24`; ADR-0014 Consequences (GAP-1 RESOLVED block); `.github/workflows/ci.yml`;
`.envrc`.

`doc.go`'s "Resolution" section and ADR-0014's Consequences both state that
`GOPRIVATE=github.com/denkhaus/dagmar` "skips the public proxy + sumdb (needed for a newly-published
module until sum.golang.org records it)" — i.e. GOPRIVATE is presented as part of *why* the
published `require` resolves at Dagger's source-isolated load. But:

- grep finds **no** `GOPRIVATE`/`GONOSUMDB`/`GOPROXY`/`GOFLAGS` in any `.go`, CI workflow, Justfile,
  lefthook, or `.envrc` (the latter sets `GITHUB_TOKEN` only). The Dagger module-load container and
  the GitHub Actions runner therefore resolve the manifest module **with default proxy/sumdb
  behavior and no GOPRIVATE**.
- For a **public** repo that is exactly what works: `proxy.golang.org` fetches
  `github.com/denkhaus/dagmar/manifest` (VCS fallback over HTTPS, no auth), and the committed
  `go.sum` carries the `h1:` hash. GOPRIVATE is *not* required here.

So the doc/ADR overstate GOPRIVATE's role: it is neither configured nor necessary on the proven path.
Two distinct risks follow, either of which alone justifies a mend:
1. **Misleading recipe.** A reader generalizing this finding to the *next* (genuinely private, or
   freshly-published-and-not-yet-crawled) module would set `GOPRIVATE` in their shell — but CI/load
   would still lack it, so the resolution they believe they reproduced would not hold in CI.
2. **Latent flake.** For a module whose sum is not yet recorded by `sum.golang.org`, *without*
   `GONOSUMDB`/`GOPRIVATE` a fresh runner can hit a sumdb-verification failure until the sum is
   crawled. The current public module happens to resolve, but the doc claims robustness ("skips the
   proxy/sumdb") that the unwired configuration does not actually deliver.

Recommended: either (a) strike "needed" and record that **the public repo resolves without
GOPRIVATE** (proxy/VCS + committed go.sum), mentioning GOPRIVATE only as optional belt-and-suspenders
for a not-yet-crawled module; or (b) if the intent is robustness, actually wire
`GOPRIVATE=github.com/denkhaus/dagmar` into the load/CI path (e.g. `env:` in `ci.yml`, and document
how the Dagger load container receives it) and then the claim is true. As written, claim and wiring
diverge. Non-blocking for the increment (resolution demonstrably works), but this is the finding most
worth correcting before the pattern is copied.

### [FOUNDATIONS-2] The manifest module's own tests are unguarded by CI — GAP

**Severity:** medium (coverage of a security-relevant parser). **Files:** `.dagmar/project.yaml`
(checkables list); `manifest/manifest_test.go`.

`project.yaml` declares checkables for `controller` (`.`), `dagger-module` (`.dagger`),
`dagmar-project` (`.dagmar`), and `secrets` (`.`) — but **not** `manifest/`. Go's `./...` does not
cross module boundaries, so the root `controller` checkable never reaches `manifest/`, and no
checkable runs `go test` there. Consequently `manifest_test.go` (8 cases, including the
review-14 `validateWorkdir` path-escape/absolute/empty rejections — the gate's source-root
containment invariant) runs **only** on a manual `cd manifest && go test`. The consumers (`.dagger`,
`.dagmar`) compile `manifest` as a transitive dependency, but compiling a package does not run its
`_test.go` files.

The gate's claim "a broken gate is caught BY the gate" (project.yaml) does not extend to the manifest
contract itself. Recommended: add a checkable —

```yaml
- name: manifest
  workdir: manifest
  command: go build ./... && go vet ./... && go test ./...
```

—which also gives the `manifest` module a standalone-build CI signal (its own go.mod graph:
`gopkg.in/yaml.v3`), independent of whether any consumer happens to import it this week. Safe w.r.t.
the `go.work`-masking concern: in CI (no `go.work`) it builds in module mode; locally it uses the
workspace. Non-blocking; one stanza.

### [FOUNDATIONS-3] `ManifestContractVersion` is an unused anchor whose comment over-promises — GAP

**Severity:** low-medium. **Files:** `.dagger/main.go:24–29` (import + const); `manifest/manifest.go:22–25`
(`Version`).

`.dagger/main.go` imports the manifest package solely to declare
`const ManifestContractVersion = manifest.Version`. grep confirms **zero consumers** of that const —
nothing validates an incoming project manifest against it, and `gate.Gate` never references `Version`
or `ManifestContractVersion`. The comment says the platform "declares which manifest schema revision
it validates and speaks," but no validation exists. As a forward-looking, CRD-analog anchor it is
defensible (and it does have one real effect: it forces `.dagger`→`manifest` resolution at module
load, so `dagger develop`/the gate's `dagger-module` checkable exercises the published require on the
platform side too). The defect is the *claim*, not the const.

Recommended: either soften the comment ("anchor / forward-looking — not yet enforced; the gate will
assert the project's declared version against this once manifests carry a version field"), or wire a
real check (e.g. gate rejects a project manifest whose declared version is newer than
`ManifestContractVersion`). Low effort either way.

### [FOUNDATIONS-4] "Published" module is reachable only via an untagged branch-commit pseudo-version — HOUSE

**Severity:** low (hygiene / upgrade ergonomics). **Files:** `.dagger/go.mod`, `.dagmar/go.mod`
(both pin `v0.0.0-20260807182901-689517a953c6`); `manifest/doc.go:22–23`.

Both consumers pin the pseudo-version of the extract commit `689517a`, reachable today only via the
pushed feature branch (no git tags exist). It resolves correctly — `689517a` stays in history
post-merge, so the pseudo-version remains fetchable even after the branch is deleted — but a
"published shared library" consumed by pseudo-version-from-a-branch is unusual and makes deliberate
upgrades awkward (every consumer re-derives a pseudo-version). `doc.go` already says "tag at merge to
main"; reinforce as a concrete merge-time action: tag `manifest/v0.1.0` (matching
`manifest.Version = "v0.1.0"`) so the module is first-class on the proxy and consumers can
`require`/upgrade a real SemVer. Note the deliberate version-axis split: `manifest.Version` is the
**contract** schema revision (v0.1.0), independent of the **module** release tag — worth one line in
`doc.go` so a reader does not expect the two to match.

### [SPEC-2] Decision §2 table still assigns the manifest to PROJECT, now superseded — HOUSE

**Severity:** low (doc coherence). **Files:** ADR-0014 Decision §2 (assignment table row
"`.dagmar/project.yaml` (manifest) | PROJECT").

The RESOLVED block (in Consequences) correctly reframes the manifest **schema/parser** as PLATFORM
authority (the published lib IS the contract) while the manifest **instance** (`.dagmar/project.yaml`)
remains PROJECT. That is a sound and well-argued pivot — arguably the right call (a user Project
should not own the schema it must conform to). But the original Decision §2 table lists "manifest |
PROJECT" without a pointer, so a reader who stops at §2 sees the pre-resolution assignment. Recommended:
one parenthetical at the §2 row ("schema/parser → PLATFORM published lib, see Consequences GAP-1;
instance data → PROJECT") so the table does not contradict the resolution.

### [HOUSE-1] `go.work` gitignored — SOUND; two seams — HOUSE

**Severity:** low. **Files:** `.gitignore:6–11`.

The decision to gitignore `go.work`/`go.work.sum` is **sound and correctly reasoned**: a committed
`go.work` would be visible inside the gate container (the repo is mounted at `/src`), and the gate's
checkables would then resolve `manifest` via the workspace `use` directive rather than the published
`require` — masking exactly the property the gate is meant to prove. CI's fresh checkout has no
`go.work`, so CI is the honest exercise of the published-dep path (the `.gitignore` comment states
this precisely). Two minor seams:

1. **No template to reconstruct it.** The `.gitignore` rationale is elaborate but there is no
   `go.work.example` or Justfile recipe documenting the required `use` directives
   (`./manifest`, `./.dagger`, `./.dagmar`, `.`). A fresh clone cannot rebuild the workspace; the
   set of modules is non-obvious. Recommended: commit a `go.work.example` (or a `just workspace`
   recipe) alongside the gitignore entry.
2. **Coexistence with the parent `go.work`.** A *parent* workspace exists at
   `/home/denkhaus/dev/gomodules/go.work` (Justfile:4 — the reason controller-gen needs `GOWORK=off`).
   Go selects the **nearest** `go.work` walking up from the module dir, so the new repo-root
   `go.work` correctly shadows the parent for everything under `dagmar/`. This is benign (and
   desirable — more specific), but the nesting is worth a one-line note so the two workspaces are not
   mistaken for a misconfiguration.

### [HOUSE-2] Dual package-doc comment block — HOUSE

**Severity:** low (polish; not CI-blocking — the gate runs build/vet/test, no doc linter).
**Files:** `manifest/manifest.go:1–12` vs `manifest/doc.go:1–24`.

`manifest.go` opens with a multi-paragraph header sitting immediately above `package manifest`
(lines 1–12), while `doc.go` carries the canonical `// Package manifest …` (lines 1–24). Two
doc-comment blocks attached to the same package clause is a `golint`/`ST1000` smell ("package comment
should be in one file"). This carried over from the old `.dagmar/internal/config/manifest.go`, but a
*published* library is held to a higher bar. Recommended: trim `manifest.go`'s preamble to a
file-scope note separated from the `package` clause by a blank line (so it is not parsed as the
package doc), or fold its content into `doc.go`.

### [HOUSE-3] `.dagger` now carries a `yaml.v3` (+ test-cluster) transitive tax to read one string — HOUSE

**Severity:** low (informational). **Files:** `.dagger/go.mod`/`go.sum`
(`gopkg.in/yaml.v3` indirect + `kr/pretty`/`kr/text`/`rogpeppe/go-internal`).

Because `manifest` imports `gopkg.in/yaml.v3` at package scope, any importer — including `.dagger`,
which references only the `Version` string constant — pulls the `yaml.v3` graph (and its
`kr/pretty`/`kr/text`/`rogpeppe/go-internal` cluster) into its module graph/go.sum. This is an
expected and acceptable cost for a shared contract library the platform will legitimately parse
manifests with later; noted only so the tax is a conscious choice. (If version-pinning were ever the
platform's *only* need, a dependency-free version artifact would avoid it — but that would fragment
the contract, so the current choice is the right one.)

## 4. Verdict

**ACCEPTED** — the increment achieves exactly what dagmar-a1e0 + ADR-0014 GAP-1 asked, the
published-module approach holds up (a versioned `require` resolves at Dagger's source-isolated load
because the repo is public; relative `replace`/`vendor/` correctly rejected), and there is **no
correctness defect** — the rename is complete, the gate rewires cleanly, and OsEcoConfig is correctly
retained on the platform side.

The findings are non-blocking hardening/polish. In priority order: **FOUNDATIONS-1** (correct the
GOPRIVATE record or wire it — the central claim should match reality), **FOUNDATIONS-2** (add a
`manifest` gate checkable so its tests — incl. the path-escape invariant — run in CI), then
**FOUNDATIONS-3** (soften or wire `ManifestContractVersion`), then the HOUSE items (tag
`manifest/v0.1.0` at merge; `go.work.example`; trim the duplicate package doc). The `go.work`
gitignore itself is sound.
