## A. Standards

### A1. `[FIX]` — The functional-core validation seam is documented as the caller's job but no caller invokes it

**Location:** `.dagger/internal/app/sandbox.go` L12-15 (doc comment);
`.dagger/main.go` L84-93 (`Sandbox` method).

- `app/sandbox.go` L13-14: "_The spec is validated by the caller via the pure
  `domain.SandboxSpec.Validate` (functional core); this function only applies the Dagger
  binding._"
- `main.go` L92: `return &Sandbox{ctr: app.BuildSandbox(domain.SandboxSpec{Image: image,
  Workdir: workingDir})}` — constructs the spec and delegates **without ever calling
  `Validate()`**.

The pure `Validate()` (`.dagger/internal/domain/sandbox.go` L21-26) is the headline payoff
of ADR-0010 §3 ("the pure decision logic … maximally unit-testable"), and it *is* tested
(`domain/sandbox_test.go`). But on the only live path it is **dead code**: an empty `image`
flows straight into `Container().From("")` and surfaces as an opaque engine error instead
of the clean `domain: SandboxSpec.Image is required`. The functional core guards nothing
today because the seam never consults it.

**Recommend:** make the contract real — `Sandbox` should return `(*Sandbox, error)` and
call `spec.Validate()` before delegating (or `BuildSandbox` returns `(*Container, error)`
and validates at the top, so a future caller can't skip it). Then `dagger develop`. Low
*functional* severity (it fails safe at the engine, not wrong output), but it is a
documented contract that is not honored — the cleanest, most concrete fix in this pass.

## B. Spec

### B1. `[GAP]` `[SPEC]` — The §7 mock-based test strategy is declared but not realizable: `go.uber.org/mock` is not a module dependency and no mock is generated

**Location:** `docs/adr/0010-go-module-layout.md` §7 (Testing);
`.dagger/internal/ports/oseco.go` L5 (doc comment); `.dagger/internal/ports/generate.go`
L9 (directive).

ADR-0010 §7 specifies "_`app/` port-logic — unit-tested against `mockgen`-generated mocks
of the os-eco ports (`go.uber.org/mock` …)_", and `ports/oseco.go` L5 repeats "_Mocks are
generated by mockgen (`go.uber.org/mock`) — see generate.go_". Verified against the module:

- `mock_oseco.go` **does not exist** in the tree.
- `go mod why go.uber.org/mock` → _"(main module does not need package go.uber.org/mock)"_.
- `go generate -n ./internal/ports/...` → `go run go.uber.org/mock/mockgen -source=oseco.go
  …` — i.e. the tool is invoked as an **ad-hoc `go run`** (resolving on the fly), not as a
  declared, reproducible module dependency.

So the documented `app/` port-logic test tier has nothing to import: the first such unit
test cannot be written against a committed mock, and a fresh checkout running
`go generate ./internal/ports/...` depends on live network to fetch the tool rather than on
`go.mod`. This drifts from the seed's ask (a testable skeleton) specifically on the
mock-backed tier ADR-0010 promises.

**Recommend:** either (a) land it now — add `go.uber.org/mock/mockgen` to `go.mod` (a
`tools.go` or `//go:build tools` pattern keeps it out of the runtime binary) and commit
`mock_oseco.go`; or (b) if mocks are intentionally deferred until the first port-logic
test, reword ADR-0010 §7 and the `ports/oseco.go`/`generate.go` comments to say "generated
on first app port-test" so the doc matches the deferred state. Prefer (a) — the strategy is
the spec.

## D. Undefined / under-defined terms

### D1. `[GAP]` (low) — `envconfig` is referenced as decided but is not a module dependency

**Location:** `.dagger/internal/config/config.go` L13-15 (`envconfig:"SEEDS"` etc. tags);
`docs/adr/0010-go-module-layout.md` §8 ("Config: `envconfig` sub-structs").

`config.OsEcoConfig` carries `envconfig:"…"` struct tags, and ADR-0010 §8 names envconfig
as the runtime-config mechanism. `go mod why github.com/kelseyhightower/envconfig` →
_"(main module does not need package …)"_. The tag *syntax* commits to the
kelseyhightower library while no resolver is wired — which the `config.go` comment does
acknowledge ("prefix added at a parent struct when a resolver is wired in"). Not a build
break (tags are opaque strings), but the doc presents envconfig as decided while the dep is
absent.

**Recommend:** add the dependency when the resolver lands, or soften the doc/ADR wording to
"envconfig-style tags (resolver TBD)". Low severity — deferred by design.

## F. Housekeeping

### F1. `[HOUSE]` — Two same-shape os-eco structs coexist with only a prose bridge

**Location:** `.dagger/main.go` L42-49 (`OsEcoBinding{Seeds,Mulch,Canopy}`);
`.dagger/internal/config/config.go` L12-16 (`OsEcoConfig{Seeds,Mulch,Canopy}`).

The triple `{Seeds, Mulch, Canopy}` is duplicated across the constructor seam
(`main.OsEcoBinding`) and the env-config struct (`config.OsEcoConfig`). The `config.go`
comment says the manifest binding is "_surfaced via main.OsEcoBinding at the constructor
seam_", but there is no code or doc line stating how the two reconcile (which source wins
at runtime, whether they merge). That mapping is prose-only — exactly the kind of
undocumented field→primitive bridge the review looks for.

**Recommend:** once the env resolver lands, either add a one-line relationship note in
`config.go` or extract a shared internal type both embed. Low severity today.
