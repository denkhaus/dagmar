## 2. Findings

### [FIX-1] §5 Rule 1 asserts a hard sandbox network-restriction that ADR-0011 explicitly rejects — and it is the rule supposed to backstop the others
**Severity:** high (hermeticity / contradiction with an ACCEPTED ADR). **Section:** ADR-0013 §5, Rule 1.

Rule 1 states: *"the in-loop sandbox independently guarantees hermeticity (network-restricted, FS read-only except the workspace). A misclassified 'read' cannot escape."* This directly contradicts ADR-0011, which is ACCEPTED and evidence-backed:

- ADR-0011 §2 Terminology: *"'Hermetic' = the LLM is not handed a tool it can call to reach the network, not that no network path exists anywhere in the Sandbox. Readers must not over-trust 'hermetic' as 'cannot reach the network under any path.'"*
- ADR-0011 §3 (ProbeNet): *"a container exec has outbound network by default … an injected instruction could in principle reach the network via a raw exec path … independent of the `Env` tool-set."*

So the backstop Rule 1 relies on **does not exist**: there is no per-exec no-network mechanism (ProbeNet, `ContainerWithExecOpts` has no network field). Under ADR-0011's actual model, a misclassified "read" command that performs network egress **can** escape, because the container exec has outbound network. Rule 1 is also the defense-in-depth that is supposed to catch Rule-3 misclassification (read-local vs network) — so the break propagates: manifest classification of read-local vs network becomes a load-bearing invariant with **no** sandbox backstop.

The secondary sub-claim, *"FS read-only except the workspace,"* is likewise unsupported: no prior ADR establishes an FS-isolation lever; ADR-0011 is purely a tool-surface statement.

**Recommendation:** rewrite Rule 1 to ADR-0011's tool-surface model — hermeticity = *no network-capable tool is handed to the LLM* (which is exactly what the manifest→tool wrapping must guarantee) — and state explicitly that there is **no** sandbox network backstop (ProbeNet residual, ADR-0011 §3). Then either drop "FS read-only" or cite the mechanism that enforces it. The actual hermeticity backbone is Rule 3 (read-local) + Rule 4 (writes gated), both of which are consistent with ADR-0011; Rule 1 should support them by *restating the real control*, not by inventing a harder one.

### [GAP-1] D6/D7 serialize/sequence at Project granularity, but the deferred question, CONTEXT.md, and ADR-0008 §5 are all Task-granularity — and the justification is circular under the documented Workspace model
**Severity:** high (model divergence). **Sections:** ADR-0013 §3 D6/D7; cf. CONTEXT.md `Workspace`, `Open questions`; ADR-0008 §5; `dagmar-67bc` scope #3.

Three facts compound:

1. **Wrong question answered.** The deferred item (dagmar-67bc #3, ADR-0008 §5, ADR-0004 open-questions, CONTEXT.md "Open questions") is *"concurrent Runs on one **Task**."* D6/D7 answers *"one dispatching Run per **Project**."* A Project is 1:N Tasks; per-Project serialization is strictly stricter and blocks concurrent Tasks on different branches within one Project. The ADR never notes it is answering a different-granularity question, nor argues why Project is the right cut.
2. **Circular justification.** D6 justifies serialization thus: *"the workspace (the repo checkout on the cache-vol) is shared mutable state; two agents editing one checkout corrupt it."* But CONTEXT.md defines `Workspace` as *"Strictly isolated per Run (no shared clone — avoids file-change collisions)"* and *"per-Task base ref; per-Run isolated clone."* Under the documented model, two Runs in a Project do **not** share a checkout — so the premise only holds under a *new* (undocumented) model where the checkout is per-Project-shared on the cache-vol. The ADR silently replaces CONTEXT.md's per-Run-isolated Workspace with a per-Project-shared one to motivate its own serialization rule.
3. **Lineage storage can't represent the domain.** D7 stores a single `lineageHead` + `activeRun` on `Project.Status`. Lineage is a **Task** concept (CONTEXT.md: *"Workspace lineage across a Task's Runs"*). A single `lineageHead` cannot represent the independent lineages of multiple concurrent Tasks in one Project — which is itself a consequence of choosing Project as the unit.

**Recommendation:** pick one explicitly. Either (a) justify per-Project serialization as a **deliberate supersession** of the Task-scoped model — with a real argument (e.g. Phase-2 simplicity, single warm checkout per Project) and a corresponding CONTEXT.md update that replaces "per-Run isolated Workspace" coherently — or (b) move serialization/lineage to Task granularity (one dispatching Run per Task; lineage per Task). As written, the decision contradicts three documents and motivates itself with a premise the documents deny.

### [GAP-2] D10's engine-git-creds path sits outside both of ADR-0007's layers; asserting it "matches the two-layer defense (A1)" is premature
**Severity:** high (security / blast radius). **Section:** ADR-0013 §4 D10 + Alternatives.

ADR-0007's two layers (restated in ADR-0008 §4 / "A1") are: (1) the per-Project **namespace** (K8s RBAC, hard credential boundary); (2) **Sandbox encapsulation** — secrets projected per-Run into the Sandbox, never in the LLM-reachable environment. ADR-0007's three typed classes (`vcs`/`os-eco`/`llm`) are **all** Sandbox-projected.

D10 introduces a fourth credential path: a per-Project scoped git credential that the **singleton engine itself** uses to clone the (private) capability module. The engine is a shared DaemonSet living in a **system** namespace, not the Project namespace (Layer 1 does not bound it), and the credential is consumed by the engine process — not a per-Run Sandbox projection of the three classes (Layer 2 does not describe it). So the path is genuinely new and outside the two layers as defined. D10 nonetheless asserts *"This matches … the two-layer credential defense (ADR-0007 / A1)"* and the Alternatives section rejects "platform engine-wide git creds" on blast-radius grounds — but the argument that the chosen shape is safe **depends entirely on the unresolved mechanism** (GAP-3): safety holds only if the engine truly holds no standing cred and per-dispatch injection never persists and never crosses Projects. None of that is established.

**Recommendation:** do not claim ADR-0007/A1 consistency for a path ADR-0007 never contemplated. Instead name the tension explicitly and state the **invariant the spike must preserve**: the engine holds no standing credential; per-dispatch injection is ephemeral and never visible across Projects; any engine-side credentialed operation is confined to one Project's scoped token. Mark satisfaction of that invariant as spike-gated (see GAP-3), not as already-decided.

### [GAP-3] Spike (a) boundary is mis-drawn: "the singleton engine holds no broad creds" is a spike-gated security outcome, not a settled design input
**Severity:** medium (spike scoping). **Section:** ADR-0013 §4 D10 spike note; Consequences; Deferred.

D10 frames the engine-git-creds work as *"design fixed (per-Project scoped, engine holds none), mechanism open (how the engine receives per-dispatch scoped creds)."* But *"the engine holds no standing credential"* is precisely the property whose feasibility under Dagger v0.21.x the spike must determine. If the only v0.21.x mechanisms for passing git credentials to the engine require an engine-side git credential helper, a persisted cred store, or an env var on the engine process, then *"engine holds none"* is **not** achievable — and the result is exactly the engine-wide-cred blast radius D10's Alternatives rejects. The boundary therefore leaks a load-bearing security claim into "mechanism."

**Recommendation:** restate the spike as deciding two things — (1) the v0.21.x mechanism, and (2) **whether** that mechanism can satisfy the "no standing engine cred" invariant. Until (2) confirms, treat "engine holds none" as a **desired invariant**, not a design premise, and keep D10's ADR-0007-consistency claim conditional on it.

### [GAP-4] D12's feasibility rests on an unstated assumption about the Dagger LLM primitive's tool-registration surface
**Severity:** medium (feasibility risk). **Section:** ADR-0013 §5 D12 + spike note.

D12's entire design — manifest-declared bash commands wrapped into dedicated per-Project LLM tools (`issues_read`, `expertise_write`, …) — assumes the Dagger LLM primitive supports **dynamic, per-Project tool registration from arbitrary declared commands**. The spike note gestures at this (*"depends on the primitive's tool-registration surface (Phase 2 cognition)"*) but frames it as the wrapping **mechanism**. If the primitive's tool surface is static (tools fixed at Env construction, not data-driven per Project), then D12 is not implementable without upstream changes — i.e. the **design** (not merely the wrapping detail) is spike-gated.

**Recommendation:** state the assumption explicitly: D12 requires the primitive to expose a data-driven tool-registration surface. Flag primitive feasibility (can manifest bash commands become real LLM tools at all?) as the spike's first question, ahead of the hermeticity/argv mechanics.

### [GAP-5] D7's `activeRun` serialization pointer is a single point of blocking for a whole Project, with no stated crash/stale-pointer recovery
**Severity:** medium (robustness). **Section:** ADR-0013 §3 D7.

`activeRun` on `Project.Status` is the serialization gate: a new Run for that Project requeues while `activeRun` is set, cleared on terminal. Because it gates an entire Project, a stuck `activeRun` blocks **all** future work for that Project. The ADR does not specify recovery when the controller or pod dies mid-flight:

- D3 requeues on observed pod transitions. If the pod is removed **without** an observable terminal state (node failure, force-delete, eviction) and the controller last set `activeRun`, on reconcile the controller sees Pod NotFound while `activeRun` is still set — there is no stated rule that clears it.
- Owner-ref GC reclaims the pod when the **Run** is deleted, but `activeRun` lives on `Project.Status`, not the Run; nothing in D4/D5 ties `activeRun` clearance to Run/Pod absence.

**Recommendation:** define terminal/clear semantics for `activeRun` explicitly — e.g. clear when the referenced Run reaches a terminal *Condition* **or** the Run/Pod is absent on reconcile; state the reconcile rule that turns "pod gone, non-terminal Run" into a terminal Run (and thus frees the pointer). Without this, a single lost pod can head-of-line-block a Project indefinitely.

### [HOUSE-1] §5 Rule 2 overstates argv-safety: manifest commands are bash bodies, so "removes shell-injection as an attack surface" holds only under implementation + manifest discipline
**Severity:** low (precision). **Section:** ADR-0013 §5, Rule 2.

Rule 2: *"the tool wrapper passes LLM-supplied args as separate argv elements (or strictly escaped), never raw into a shell string. This removes shell-injection as an attack surface."* D12 declares the bindings as **bash commands with placeholders**, so the wrapper invokes a shell (`bash -c '<body with $1>' -- <args>`, or similar). argv-safety then depends on (a) the wrapper's invocation form and (b) the manifest body not re-interpolating the placeholders unsafely. It is a real reduction of surface, not its elimination — and the mechanism is itself spike-bound (GAP-4).

**Recommendation:** soften to "substantially reduces shell-injection surface **when** the wrapper argv-applies placeholders and the manifest body does not re-interpolate them," and note this is a property the wrapping spike must enforce.

### [HOUSE-2] D6's cross-Project-parallel safety asserts isolation without restating the controller invariant it rests on
**Severity:** low (precision). **Section:** ADR-0013 §3 D6.

D6: *"Different Projects run concurrently (isolated cache-vols + namespaces, ADR-0008 …)."* Per ADR-0008 §3, that isolation is a **controller** guarantee, not an engine invariant: cache isolation *"is prevented as long as Projects never share a cache-volume name"* — the controller allocates distinct names. D6 presents the isolation as given; a future controller bug that reuses a cache-vol name (or a namespace collision) silently breaks cross-Project parallelism's safety premise.

**Recommendation:** add one clause: cross-Project parallelism is safe **contingent on** the controller's distinct-cache-vol-name + distinct-namespace allocation invariants (ADR-0008 §3), which this ADR's provisioning design must preserve.

### [HOUSE-3] D9 makes `agent-pod-image` "optionally overridable on `Agent.spec`" while the Alternatives reject "on `Agent.spec`" — needs a reconciling sentence
**Severity:** low (internal tension). **Section:** ADR-0013 §4 D9 vs Alternatives.

D9 chooses a platform default *"optionally overridable on `Agent.spec`."* The Alternatives reject `agent-pod-image` on `Agent.spec` because it *"conflates persona with pod template."* Optional override partially reintroduces that conflation. The two are reconcilable (the rejection is of making it **fixed/mandatory** on `Agent.spec`; an optional escape hatch is different), but the ADR should say so rather than leave the reader to infer it.

**Recommendation:** one sentence in D9 distinguishing "mandatory/fixed on Agent.spec (rejected)" from "optional override (chosen)" and why the optional form does not re-conflate.

### [HOUSE-4] D4's finalizer is namespace-scoped, but the warm-retained cache-vol is an engine-side object outside the namespace; reclaim is currently unowned
**Severity:** low (operational ownership). **Section:** ADR-0013 §2 D4.

D4: the `Project` finalizer tears down SA + `RoleBinding`s, and the cache-vol is **retained** (warm) with reclaim deferred. Per ADR-0008 §3, cache identity is **engine-side** (the store keys by volume name), so the retained cache-vol is not a namespace object and is not touched by the namespace-scoped finalizer. Until a reclaim policy exists, there is an engine-side growth path with no named owner.

**Recommendation:** state explicitly that warm retention leaves an **engine-side** artifact outside the Project namespace, and name where reclaim ownership will live (controller, engine, ops) when that increment arrives.

### [HOUSE-5] "dispatching Run" (D6) is used load-bearingly but not pinned
**Severity:** trivial (terminology). **Section:** ADR-0013 §3 D6.

D6's invariant is "at most one **dispatching** Run at a time." "Dispatching" is not pinned to a status Condition (D5's set is `Accepted/Progressing/Succeeded/Failed`; §2 also uses `Dispatched` for pod-Running). A reader cannot tell whether "dispatching" = `activeRun` set, = past `Accepted`, or = `Progressing`/`Dispatched`. The invariant's meaning depends on which.

**Recommendation:** define "dispatching Run" in terms of `activeRun`/the Condition set so the serialization rule is unambiguous.

### [SPEC-1] The two spikes are referenced (Consequences/Deferred) but are not filed in the tracker
**Severity:** informational (process). **Section:** ADR-0013 Consequences/Deferred.

ADR-0013 states *"Two spikes are filed out of this ADR."* The tracker (`.seeds/issues.jsonl`, 14 seeds) contains **neither** an engine-git-creds nor an os-eco-tool-wrapping seed. The repo convention (ADR-0004/0007 "filed, not gating" pattern) is that deferrals land in seeds so they are trackable. Given GAP-3/GAP-4 show these carry design weight, filing them is the cheapest way to keep them visible.

**Recommendation:** file both spikes as seeds (type `task`/`spike`, depending on `dagmar-67bc`), or reword the ADR from "filed" to "to be filed," so the doc matches the tracker.

"No worker pool" is correctly argued (a worker pool would duplicate the execution layer the agent pods already are). ✓
- **ADR-0006 (merge = controller function, never LLM):** correctly restated in the "Already decided" block and honored (merge tool in no tool-set; nothing in D8–D12 hands merge to an Agent). ✓
- **ADR-0007 (two-layer defense) + A1:** the **intent** (per-Project scoped, no engine-wide cred) is in the right direction, but the consistency claim is premature — see GAP-2/GAP-3. ✗ (load-bearing)
- **ADR-0008 (singleton engine; per-Project SA + `pods/exec` + cache-vol names):** D8–D10 provision exactly this; cache-vol retention (D4) is consistent with the iteration-speed value. D6's cross-Project parallelism rests on ADR-0008 §3's distinct-name invariant — see HOUSE-2. The deferred concurrency/lineage item ADR-0008 §5 forwards is *answered*, but at a different granularity — see GAP-1. ⚠
- **ADR-0010 (hexagonal; port/adapter):** D12's framing of os-eco bindings as manifest-declared tool-ports is a sound application of the hexagonal idea (port = the abstract tool, adapter = the manifest command) and of the manifest=what / wrapper=how split. ✓ (feasibility caveat: GAP-4)
- **ADR-0011 (hermeticity = tool-surface, ProbeNet residual):** **contradicted** by §5 Rule 1 — see FIX-1. The os-eco rules' *backbone* (Rule 3 read-local + Rule 4 writes-gated) is consistent with ADR-0011; only Rule 1 overclaims. ⚠ (load-bearing)
- **ADR-0012 (lean, growing trajectory):** the deferrals (admission webhooks D2; cache-vol reclaim D4; object-storage schema D11; event/trigger model) are consistent with lean-growing and with cognition-before-autonomy. Designing 12 decisions ahead in a PROPOSED ADR is appropriate (this is design, not implementation). ✓
- **CONTEXT.md:** **diverges** on the Workspace/concurrency model — see GAP-1. If per-Project serialization is kept, CONTEXT.md's `Workspace` ("per-Run isolated, no shared clone") and `Open questions` ("concurrent Runs on one Task") must be updated to match, or the decision re-scoped to Task granularity.

## 5. The os-eco tool-port hermeticity argument (§5, five rules)

- **Rule 1 (read-only = contract AND sandbox-enforced):** broken — see FIX-1. The claimed sandbox backstop does not exist under ADR-0011; "a misclassified read cannot escape" is false.
- **Rule 2 (placeholders → argv):** sound in direction, overstated in absolutism — see HOUSE-1.
- **Rule 3 (in-loop reads are read-local / network-free):** sound and consistent with ADR-0011 §9. This is the rule that actually carries hermeticity. Its correctness now depends entirely on manifest classification — which Rule 1 falsely claimed to backstop. After FIX-1, manifest read-local-vs-network classification becomes a **reviewable load-bearing invariant** in its own right; the ADR should say so.
- **Rule 4 (writes in a separate networked context, never in-loop):** sound; realizes ADR-0011 §9 as a tool-availability rule. ✓
- **Rule 5 (home = manifest, not the Project CR):** sound design principle; correctly keeps project-specific, versioned content in the repo. ✓

Net: the argument's **backbone (Rules 3+4) holds**; its **claimed defense-in-depth (Rule 1) does not**. Fixing Rule 1 (to the tool-surface model) and naming manifest classification as the primary control yields a coherent hermeticity story.

## 6. Concurrency model — shared-state paths

- **Per-Project serialization (D6):** the unit is wrong relative to the domain (GAP-1), and the stated reason (shared workspace) assumes an undocumented model. The mechanism itself (controller-owned `activeRun`) is reasonable *for whatever unit is chosen*.
- **Cross-Project parallel (D6):** safe *contingent on* controller invariants (distinct cache-vol names + namespaces) the ADR does not restate (HOUSE-2).
- **Singleton engine as shared state:** ADR-0008 §5 accepts native per-session isolation; D6 adds no new engine-shared hazard **except** the engine-git-creds path, which makes the shared engine a (transient) credential holder — that is the new cross-Project risk surface (GAP-2). No other cross-Project namespace-leakage path is introduced (namespaces + RBAC per ADR-0007 §1 are preserved).
- **Shared agent-pod-image (D9):** not a concurrency race (images immutable); a supply-chain compromise hits all Projects, but that is a security consideration, not a concurrency one — out of this ADR's scope.

---

## 7. Conclusion

ADR-0013 is a serious, well-structured design that genuinely resolves the `dagmar-67bc` scope and cashes in several deferrals. The reconciliation model (D3–D5) and the provisioning field homes (D8–D9) are SOUND. However, **three high items block ACCEPTED**: FIX-1 (a hermeticity claim that contradicts the ACCEPTED ADR-0011 and undermines the os-eco rules' own defense-in-depth), GAP-1 (a concurrency/lineage granularity that conflicts with CONTEXT.md, ADR-0008 §5, and the seed scope, justified by a Workspace model the docs deny), and GAP-2 (an ADR-0007-consistency claim for a credential path that sits outside both of ADR-0007's layers and depends on an unresolved mechanism). GAP-3/GAP-4 sharpen the two spikes so their boundaries stop leaking security/feasibility weight; GAP-5 closes an unspecified crash-recovery for the serialization pointer; the HOUSE/SPEC items are precision and tracking.

**Verdict: NEEDS-WORK.** Reconcile FIX-1, GAP-1, GAP-2 (and file the two spikes, SPEC-1) before moving PROPOSED → ACCEPTED; the remainder can land as sharpening.

**Summary of findings:** 1 FIX, 5 GAP, 5 HOUSE, 1 SPEC.
