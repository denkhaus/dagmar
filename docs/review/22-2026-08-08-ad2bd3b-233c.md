### B. Undefined / under-defined terms

### C. Referenced-but-missing ADRs

**None.** The token injection here is PROJECT-scope (dagmar-as-a-project's own gate-family,
ADR-0014): it is a local CI/developer convenience, not a platform-level credential-class
decision. ADR-0007's three typed secret classes (`vcs` / `os-eco` / `llm`) govern the
platform's per-Project credential injection into Sandboxes — a different layer. A `GITHUB_TOKEN`
for rate-limit relief in a build container is an infrastructure credential, not a Project
runtime credential, and does not need an ADR. The use of `WithSecretVariable` (not
`WithEnvVariable`, not baked into the image) is consistent with ADR-0007's spirit
(Alternatives: "credentials baked into the agent image — rejected").

### D. Documentation structure / housekeeping

#### [GAP-1] lefthook pre-push now hard-depends on `GITHUB_TOKEN` in the local environment — the nil-safety does not protect the CLI layer

**Severity:** medium (developer-experience regression). **Files:** `lefthook.yml:24`;
`.envrc`.

The spec states "Optional, token nil-safe so callers without it still work (unauthenticated,
as today)." The **API-level** nil-safety is correct: `bootstrapBase` checks `githubToken != nil`
and skips the `WithSecretVariable` call. But `lefthook.yml` now invokes
`--github-token env:GITHUB_TOKEN` unconditionally. The `env:` prefix is a Dagger **Secret
source** that reads from the calling process's environment — if `GITHUB_TOKEN` is unset, Dagger
errors at the CLI level *before* the Go function ever receives a nil. So the nil-safe path is
only reachable when the parameter is **omitted** entirely (`dagger call ... dagmar-gate --source .`),
which the committed lefthook command never does.

Consequence: a developer who clones the repo, installs mise + lefthook, but has not set up
direnv/`.envrc` (which uses `gopass show -o ...`), gets a **broken pre-push hook** — a
regression from before this change (the hook worked with no token). CI is unaffected
(`GITHUB_TOKEN` is always available in GitHub Actions).

This is a reasonable assumption for the owner's own setup (direnv + gopass are pre-existing),
and making the token optional in the committed hook would require a shell conditional
(`${GITHUB_TOKEN:+--github-token env:GITHUB_TOKEN}`), which Dagger's `mise exec --` shell may or
may not expand correctly. Worth documenting as a setup prerequisite (e.g. a one-liner in the
lefthook.yml comment or a README/CONTRIBUTING note) so a new contributor is not surprised.

#### [HOUSE-1] `DagmarBootstrap` gained the token param, but no current caller exercises it

**Severity:** low (informational — not a defect). **Files:** `.dagmar/main.go:28–43`;
`.dagmar/internal/workflows/bootstrap.go:59`.

The spec's caller-side changes name only `dagmar-gate` (ci.yml + lefthook.yml). The
implementation additionally added `githubToken *dagger.Secret` to `DagmarBootstrap` and
`Bootstrap`. This is **structurally necessary** — `bootstrapBase` now requires the param, so
`Bootstrap` must pass it, and exposing it on `DagmarBootstrap` (the public Dagger function) is
the consistent choice (a standalone `dagmar-bootstrap` call benefits from the same rate-limit
relief). No CI/lefthook invocation calls `dagmar-bootstrap` today, so the param is unused by any
committed caller. Defensible and correct; noted only for completeness.

### E. Implementation maturity

#### [HOUSE-2] `WithSecretVariable` is cache-key-neutral — correct, but the cache interaction is subtle enough to merit a one-line note

**Severity:** low (clarity). **Files:** `bootstrap.go:39–47`.

The choice of `WithSecretVariable` (not `WithEnvVariable`) is correct and well-justified by the
comment. The subtle interaction: because secrets are **not** part of the Dagger cache digest, the
`mise install` exec layer has the **same cache key** whether or not the token is present. This
means:

- **Cache hit** (tools already rolled out from a prior run): `mise install` does not re-execute;
  ubi makes zero API calls — the token is irrelevant. ✓
- **Cache miss** (mise.toml changed, or first run): `mise install` re-executes with the token
  available → ubi authenticates → 5000 req/hr. ✓

This is the **right** behavior: the token is available exactly when ubi needs to call the API
(cache miss), and absent when it doesn't (cache hit). The current comment explains the
*security* rationale ("not baked into the cache key nor exposed in exec output") but not the
*cache-hit* interaction. A one-line addition ("on a cache hit `mise install` does not re-execute,
so the token is only exercised on a cache miss — the rate-limit relief applies exactly when ubi
calls the API") would make the design self-documenting. Optional polish.

#### [HOUSE-3] Token rotation does not invalidate the bootstrap layer — sound

**Severity:** n/a (positive verification). **Files:** `bootstrap.go:43`.

Because `WithSecretVariable` is cache-key-neutral, rotating the `GITHUB_TOKEN` (e.g. a new PAT,
or GitHub Actions rotating the ephemeral token per-run) does **not** invalidate the cached
`mise install` layer. CI therefore does not re-run `mise install` on every push just because
the ephemeral `GITHUB_TOKEN` changed — the toolchain rollout stays cached by `mise.toml` content,
as intended. Confirmed: the only `WithEnvVariable` on the path is `PATH` (bootstrap.go:48),
which is a static string and does not vary per-run.

optional cache-interaction note) are informational polish, non-blocking.
