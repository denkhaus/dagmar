## 2. Findings

### [GAP-1] The RBAC ledger is incomplete — the SA/Role/RoleBinding *create* verbs move Run→Project reconciler, but `Consequences` only documents the loss, not the gain

**Severity:** medium (completeness of the decision's blast radius — exactly the review-17 GAP-1 shape:
a Consequences omission, not a decision defect). **Files:** ADR-0015 `Consequences` L130–133;
`internal/controller/run_controller.go:63–72`.

`Consequences` states: RBAC **additions** on the ProjectReconciler = `projects/finalizers:update`
+ `projects/status` (+ existing `projects:get;list;watch`); and the RunReconciler's
`serviceaccounts`/`roles`/`rolebindings` create verbs are **dropped**. But Decision §2 puts the
**creation** of the SA `dagmar-agent-<project>` and the engine-ns `dagmar-agent-exec-<project>`
Role + RoleBinding on the **ProjectReconciler**. Those verbs therefore do not vanish — they
**migrate** from the RunReconciler to the ProjectReconciler. The "additions" list enumerates only
`projects/*` and is silent on the `serviceaccounts`/`roles`/`rolebindings`
`get;list;watch;create;update;patch` the ProjectReconciler must carry to realize §2.

An implementer marking the ProjectReconciler's RBAC from this ADR as written would give it
`projects/*` only; SA/Role/RoleBinding creation would then 403. The intent is unambiguous in §2;
the *ledger* in `Consequences` is what is incomplete. Recommended: add to `Consequences` that the
ProjectReconciler carries the `serviceaccounts`/`roles`/`rolebindings` verbs the RunReconciler
relinquishes (Role/RoleBinding are created in the **engine** namespace, a namespace other than the
Project's — worth naming, since it is the first cross-namespace create by a dagmar reconciler).
Non-blocking; a one-paragraph mend before PROPOSED→ACCEPTED.

### [SPEC-1] The realized path is a *third* option the D4 deferral note and seed framed as a binary — lifting the note must record the actual mechanism, not just "resolved"

**Severity:** low–medium (decision-record honesty). **Files:** ADR-0015 §1 (Q1=C), §5; ADR-0013 §2
D4 deferral note L83–88; seed `dagmar-54c9`.

The D4 deferral note (ADR-0013 L85–88) and seed `dagmar-54c9` both frame the unblock as a binary:
**either** (a) per-Run-named identity **or** (b) per-Project **namespace** provisioning + a
`ProjectReconciler`. ADR-0015 picks neither literally: it makes identity **per-Project-named**
(`dagmar-agent-<project>`) **in a shared namespace** + a ProjectReconciler — a third hybrid
(coarser than (a), no namespace migration like (b)). The decision is **well-justified** (per-Project
naming achieves per-Project lifecycle granularity *without* the namespace migration cost §5
defers) and satisfies the note's *substantive* requirement ("drop or re-scope the SA controller
owner-ref so its GC no longer cascades"). But the realized branch is not in either source's
enumeration.

ADR-0015 `Consequences` says the D4 note "is lifted (D4 realized, not deferred)." Lifting must not
read as "the binary was resolved" — the note's two-option framing is *superseded by a third*. Recommend
the lift records the actual chosen mechanism (per-Project-scoped identity, shared namespace,
ProjectReconciler) so the supersession is honest, mirroring the ADR-0014 GAP-1 / D4-note honesty
pattern the ADR itself cites.

### [SPEC-2] §5's interim is sound, but "per-Project-scoped identity" can be misread as "per-Project isolation achieved" — the ADR should disclaim credential isolation explicitly

**Severity:** low–medium (security framing; the decision is safe, the *claim* is over-readable).
**Files:** ADR-0015 §1, §5; ADR-0007 §1/§5; ADR-0008 §4.

The interim is **verified sound**: the two hazards are identity-*lifecycle*-scoped (safe deletion),
and the credential boundary is orthogonal — ADR-0007 §5 projects only the classes a given Run needs
into the Sandbox *regardless of the SA*, and the agent SA carries no `secrets` verbs (only engine-ns
`pods/exec`+`pods:get`, run_controller.go L212–214), so the SA is the exec-into-engine identity, not a
credential holder. Crucially, ADR-0015 does **not** introduce a new namespace divergence — per-Project
namespaces are already absent (all Runs in `default`; ADR-0013 L83-84), so the ADR *inherits and
records* an existing gap rather than creating one. Per-Project-naming even *improves* cross-Project
identity separation in `default` (Project A's pods cannot bind Project B's exec RoleBinding).

But "per-Project-scoped identity" reads, at a glance, as if per-Project isolation is delivered. It is
not: with every Project in `default` and the controller holding `secrets:get` (L69), the
namespace-scoped credential defense-in-depth layer (ADR-0007 §1, ADR-0008 §4) remains **entirely
absent** — exactly as today. The ADR's scoping is correct; the *wording* invites an over-read.
Recommend one explicit clause in §5: "this ADR provides safe identity *lifecycle*; it provides **no**
cross-Project credential isolation — that remains wholly on the deferred namespace layer." Prevents a
future reader treating the interim as a security boundary.

### [HOUSE-1] `projects/status` "(if any)" leaves whether the ProjectReconciler realizes D5's Project conditions `{Provisioned,Ready}` undecided

**Severity:** trivial–low (ambiguity). **Files:** ADR-0015 `Consequences` L131; ADR-0013 §2 D5
(L92–93).

`Consequences` lists `projects/status` "(Project status writes, **if any**)" — a hedge. ADR-0013 D5
pins `Project {Provisioned, Ready}` as the Project condition set, and `ProjectStatus` exists
(`project_types.go` L57–58) but is written by nothing today. ADR-0015 §2 (the ProjectReconciler's
reconcile body) never says whether it sets `Provisioned`/`Ready` when identity is provisioned. Either
commit ("the ProjectReconciler writes `Provisioned`/`Ready` per D5 once identity is reconciled, so
`projects/status` is required") or drop the verb and the hedge. As written, an implementer cannot tell
whether D5's Project half is realized in this increment or deferred again.

### [HOUSE-2] Migration lumps the old SA (GC'd with its creating Run) and the old engine-ns Role/RoleBinding (a finalizerless eternal leak — the bug being fixed) as one "harmless duplicate"

**Severity:** low (migration accuracy). **Files:** ADR-0015 `Consequences` L142–146.

The migration note says the stale `dagmar-agent` SA + `dagmar-agent-exec` Role/RoleBinding are
"orphaned … harmless duplicates; no Project owns them, no finalizer touches them." Two inaccuracies:
the old SA is **not** orphaned today — it is controller-owner-ref'd to its *creating* Run
(run_controller.go L196), so it GC's when that Run deletes (it self-cleans); whereas the old
engine-ns Role/RoleBinding are cross-namespace, not owner-ref'd, and have no finalizer → they
**leak indefinitely** until a manual `kubectl delete` — i.e. they are literally the dagmar-67bc bug
in the old name, not a "harmless duplicate." Recommend splitting the two: old SA → self-cleans with
its Run; old engine-ns Role/RoleBinding → eternal unless swept (call that out, don't euphemize it).
The user's "finalizerless eternal leak" concern is real for the Role/RoleBinding half.

### [HOUSE-3] ProjectReconciler `SetupWithManager` is unspecified, and "no rework" on namespace migration is slightly optimistic

**Severity:** trivial. **Files:** ADR-0015 `Consequences` L139–141; §1/§5 "same RBAC shape, no rework."

The ADR is precise about the **Run** reconciler's watch config (negatively: do **not** add
`Owns(&ServiceAccount{})` — verified correct: the SA is Project-owned, so a Run owner-ref watch is
semantically wrong; consistent with the code's D5 note at run_controller.go L443–445) but says
nothing about the **Project** reconciler's. `For(&Project{}) + Owns(&ServiceAccount{})` would be the
natural fit (the SA is Project-owned; SA changes requeue the Project) — worth stating so the
implementer does not omit the owner-watch the SA→Project ref now enables. Separately, "same name,
same RBAC shape, **no rework**" (§1/§5) is true for the *shape* but the RoleBinding `subject.Namespace`
(and the SA's namespace) *do* change when per-Project namespaces land — minor string rework, not model
rework. Qualify "no identity-model rework."

### [HOUSE-4] Wording: `C1-voll` (German) in an English ADR; the alternatives list conflates Q1 and Q2 options; "identity" is a load-bearing term not in CONTEXT.md's ubiquitous language

**Severity:** trivial. **Files:** ADR-0015 §2 header, `Alternatives`; CONTEXT.md glossary.

- `C1-voll` mixes German `voll` (= full) into an English persisted artifact — the convention
  (mx-1b17c1) is that persisted writing is English. Render as `C1-full` (or drop the shorthand in the
  header prose).
- `Alternatives considered` lists `(A)` per-Run, `(B)` full-namespace (both **Q1** granularity
  options) alongside `(C2-split)` (a **Q2** ownership option) under one flat list; §2 frames C2-split
  as the Q2 reject. Separating Q1 vs Q2 alternatives (or tagging each) avoids the read that C2-split
  is a granularity choice.
- "agent identity" / "provisioned identity" / `identity-protection` finalizer are first-class concepts
  in this ADR but `identity` has no glossary entry in CONTEXT.md (only a passing `ServiceAccount`
  mention, L37). Per ADR-0001 (Tier-C terms coined in CONTEXT.md), either add an `Identity` glossary
  line (SA + engine-ns exec RBAC, the exec-into-engine identity — *distinct* from ADR-0007 credentials)
  or ground the term on first use. Bonus coherence worth a cross-ref: this ADR *realizes a slice* of
  ADR-0007's deferred "exact RBAC RoleBindings / service-account-per-Project model" (ADR-0007
  Consequences L129) — naming that strengthens the §5 orthogonality argument.

## 3. Coherence checks (positive)

- **review-19 GAP-1 genuinely closed (§3):** verified. Today the shared-named `dagmar-agent` SA is
  `ctrl.SetControllerReference(run, sa, …)` (L196) → deleting the creating Run cascades GC and breaks
  siblings (L328 `ServiceAccountName: agentSA`). ADR-0015 owner-refs the SA to the **Project**
  (§2/§3); a Run no longer owns it, so Run deletion cannot GC it — only Project deletion cascades,
  which is the intended lifecycle. Combined with per-Project naming, the fix is real. ✓
- **dagmar-67bc leak genuinely closed (§4):** verified. The engine-ns Role/RoleBinding are
  cross-namespace (L210/L224, cannot be owner-ref'd), so §2 finalizer-cleans them on Project delete;
  per-Project naming (`dagmar-agent-exec-<project>`) makes per-Project deletion safe (one Project's
  binding cannot affect another). Removes the `dagmar-67bc` TODO at L190–191. ✓
- **D4 unblocked as written (§1):** verified. ADR-0013 D4 is a **Project-level** finalizer (L64);
  ADR-0015 delivers exactly that — no D4 revision to Run-level needed (the rejected alt (A)'s defect).
  ✓
- **ADR-0007 §5 orthogonality:** verified. The SA is the pod's exec-into-engine identity; per-Run
  projected-secret isolation (ADR-0007 §5) is independent of the SA and is untouched. Sharing the SA
  across a Project's Runs adds no new in-Project exposure (they already share `default`). ✓
- **The `<1s` race (§2) is negligible:** `NotFound → requeue` until the ProjectReconciler reconciles
  is a standard controller-runtime pattern; controller-runtime's startup reconcile pass covers
  pre-existing Projects. Benign. ✓
- **`Owns(&ServiceAccount{})` correctly stays off the Run reconciler:** verified against the code's
  D5 note (L443–445). The ADR's reasoning (Project-owned) is stronger than the code comment's stated
  condition ("until per-Run-named") — when implemented, update that comment to the per-Project reason.
  ✓

## 4. Conclusion

**Verdict: NEEDS-WORK (light).** The **decision is SOUND** and verified against the code + cited ADRs:
both live hazards are genuinely closed (review-19 GAP-1 via SA owner-ref→Project; dagmar-67bc via
per-Project-named engine-ns Role/RoleBinding + finalizer), D4 is unblocked as written (Project-level
finalizer, no revision), ADR-0007 §5 credential isolation is orthogonal and unaffected, the interim
(§5) is honest and inherits — does not introduce — the namespace divergence, and the `<1s` race is
negligible. No `[FIX]`; Q1/Q2/Q3 need no change.

The NEEDS-WORK is doc-level mends before PROPOSED→ACCEPTED:

1. **[GAP-1]** — complete the RBAC ledger: the ProjectReconciler *gains* the
   `serviceaccounts`/`roles`/`rolebindings` verbs the RunReconciler relinquishes (Role/RoleBinding

2. **[SPEC-1]** — record that the realized mechanism is a *third* option (per-Project-scoped, shared
   ns) superseding the D4 note's binary, so the note-lift is honest.
3. **[SPEC-2]** — add one clause disclaiming that this ADR delivers identity *lifecycle* only, **no**
   cross-Project credential isolation (that stays on the deferred namespace layer).

plus four `[HOUSE]` items (the `projects/status` "(if any)" hedge [HOUSE-1]; the migration euphemism
[HOUSE-2]; ProjectReconciler `SetupWithManager` + "no rework" [HOUSE-3]; `C1-voll`/alternatives
conflation/`identity` glossary [HOUSE-4]). None blocks the decision; the three mends above are the
ones that matter for an honest ACCEPTED record.
