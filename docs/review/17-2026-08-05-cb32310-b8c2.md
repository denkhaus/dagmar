## 2. Findings

### [GAP-1] The re-home is not mechanical — `gate.go` depends on the mixed-scope `config` package, which the ADR never addresses

`Consequences` asserts `.dagger/` "gives up `DagmarBootstrap`/`DagmarGate` + `workflows.{Bootstrap,Gate}`"
and `.dagmar/` "becomes a Dagger module … holds `dagmar-bootstrap`/`dagmar-gate` — moved from
`.dagger/internal/workflows/`". The move is presented as a code relocation. It is not.

- `.dagger/internal/workflows/gate.go` imports `dagger/dagmar/internal/config`
  (`config.ParseManifest` / `config.ProjectManifest` / `config.Checkable`) **and**
  `dagger/dagmar/internal/dagger`. `bootstrap.go` imports only the generated SDK + stdlib — it
  travels clean. `gate.go` does not.
- `.dagmar/` is a **new Dagger module = a new Go module** with its own `go.mod` and a module path
  that is **not** `dagger/dagmar`. Go's `internal/` rule makes `dagger/dagmar/internal/config`
  importable only by code whose import path is rooted at `dagger/dagmar` — so `gate.go`, once moved
  to `.dagmar/`, **will not compile** against the platform's `config`. (The `internal/dagger`
  import is fine: each module regenerates its own under its own path via `dagger develop`.)
- `config` is **mixed-scope**: `manifest.go` (`ProjectManifest`/`Checkable`/`ParseManifest` — PROJECT
  conformance, ADR-0003) vs `config.go` (`OsEcoConfig` — runtime/env, PLATFORM, ADR-0010 §8,
  prospective). It therefore cannot travel wholesale. A wholesale move compiles *today* only because
  `OsEcoConfig` is unused/prospective, but it mis-places platform runtime config in the project
  module and forces a re-split the moment the §8 env resolver lands.

For a scope-separation ADR, the package whose scope is actually split by this decision should be
named in the blast radius. Recommended: add to `Consequences` that `config` splits — manifest
parsing → `.dagmar/`, `OsEcoConfig` → stays in `.dagger/` — so the implementer of the deferred
increment does not discover the `internal/` wall mid-move. Non-blocking (no `Q1–Q6` decision
changes); a completeness gap in `Consequences`, not a defect in the decision.

### [SPEC-1] Coherence with ADR-0010 §4 — the split needs one explicit reconciliation sentence

ADR-0010 §4 (`docs/adr/0010-go-module-layout.md` L58–62): reusable workflow units
("`workflows/`: gate, bootstrap, review") "live as packages within `.dagger/internal/`. They are
extracted into separate Dagger modules **only when reuse crosses the dagmar boundary**." The word
"only" reads as an exhaustive trigger.

ADR-0014 extracts gate + bootstrap into a separate module **now**, before any cross-boundary reuse
(dagmar is the sole project). The triggers genuinely differ — ADR-0014 is **scope-separation**
(platform vs project conformance / making the abstraction real), not **reuse-extraction** — so this
is **not a contradiction**. But ADR-0014 never names §4's reuse-trigger to distinguish its own
scope-trigger; §6 cites §4 only for the toolchain-rollout helper (D4), not for the split itself. One
sentence in `Decision §1` or a short `Coherence` note — "this supersedes §4's in-module default for
*scope* reasons; §4's reuse-trigger is orthogonal" — closes the read. (Minor: §4 also names `review`
as a third workflow; ADR-0014 is silent on it — fine if still prospective, but a confirming clause
avoids ambiguity about a third home.)

### [HOUSE-1] Q5 "ENFORCES" risks over-reading against Q4's explicitly-deferred conformance

Q5: "The module boundary **ENFORCES** the ref-based call; the shortcuit is structurally impossible."
Verified **true for the ref**: post-split the root module (`.dagger`, `source` per root `dagger.json`)
no longer exposes `dagmar-gate`, so a bare `dagger call dagmar-gate` fails. Both live callers run with
**no `-m` today** (`ci.yml` L30 `args: dagmar-gate --source .`; `lefthook.yml` L21 pre-push
`dagger call dagmar-gate --source .`) — so both must migrate to `-m .dagmar`, exactly as `Consequences`
states. But Q4 says conformance (does the project *expose* the functions at all?) is "by ADR + naming
convention now; runtime conformance probe later." The boundary therefore enforces the **ref**, not
**conformance**. Suggest "ENFORCES the ref-based call (not conformance — see Q4)" so the caps cannot
be misread as conformance-enforcement.

### [HOUSE-2] §5 "local now is real enough" covers the abstraction, not the subpath-ref mechanism

The local ref `-m .dagmar` proves the abstraction (platform calls the project module by ref, not its
own function) and excludes the shortcuit — verified. It does **not** exercise the published subpath-ref
`-m github.com/denkhaus/dagmar/.dagmar@<ref>` at all: that is a different code path in Dagger's ref
resolver and is unproven on v0.21.8. `§5`/`Deferred` correctly defer the prototype — just qualify that
"real enough" applies to the abstraction, leaving the subpath-ref mechanism wholly unvalidated until
that prototype. Prevents a future reader assuming the local dogfood de-risks the published path.

## 3. Coherence with ADRs 0001–0013

- **ADR-0009 §2 / ADR-0012 §4** establish gate-family as PROJECT-scope ("a conforming Project must be
  a Dagger module exposing `dagmar-bootstrap` + `dagmar-gate`"). Q2's assignment
  (`DagmarBootstrap`/`DagmarGate` + `workflows.{Bootstrap,Gate}` → PROJECT) is the *consequence* of
  those ADRs, not a new claim — consistent.
- **Sandbox = PLATFORM (Q2):** verified. `main.go` L85 `Sandbox` returns the agent execution container
  (Tier A, `app.BuildSandbox`, `1 Run : 1 Sandbox`), distinct from the gate's verify container-exec
  (`bootstrapBase` in `bootstrap.go`, which runs manifest checkables). Assignment correct.
- **ADR-0011 carve-out** (gate is a *named Dagger function*, not the withheld raw `container` tool) is
  untouched by the split — the function merely changes module home.
- **ADR-0003 manifest-authoritative** preserved: `dagmar-gate` consumes `.dagmar/project.yaml`
  (manifest = what, gate = how); verified non-empty and valid (1717 B, `controller` + `dagger-module`
  checkables).

## 4. Module-boundary claim (Q1) — verified SOUND

Root `dagger.json` (`name: dagmar`, `source: .dagger`, engine `v0.21.8`) + `main.go` confirm all eight
functions today sit as methods on one `Dagmar` struct in one module — the conflation is real. The
dispatch vertical (`docs/review/13`, `dagger call -m github.com/denkhaus/dagmar probe-net`) confirms a
module is addressable by `-m <ref>` only as a whole (own `dagger.json` + source). A code-only boundary
(separate packages, one module) yields **no addressable project module** — the platform would still
call its own `workflows.Gate` as a Go function, the swap-for-another-project abstraction could not be
expressed, and the shortcuit persists. Rejecting the code-boundary is **not overstated**; it is the
correct read of Dagger's module model. The module boundary is genuinely the price of the abstraction.

## 5. Conclusion

**Verdict: NEEDS-WORK (light).** The decision itself is **SOUND** and verified against the code: the
module boundary is required (Q1), the shortcuit becomes structurally impossible (both live callers
carry no `-m` today), `Sandbox` is correctly PLATFORM (Q2), and the local-ref dogfood is real (Q5).
No `[FIX]`; `Q1–Q6` need no change. The NEEDS-WORK is two doc-level mends before PROPOSED→ACCEPTED:

1. **[GAP-1]** — pin the mixed-scope `config` package's split in the re-home (`gate.go` will not
   compile in `.dagmar/` against the platform's `internal/config`; manifest → `.dagmar/`,
   `OsEcoConfig` → `.dagger/`).
2. **[SPEC-1]** — one sentence reconciling the split with ADR-0010 §4's "only when reuse crosses the
   dagmar boundary" (scope-trigger vs reuse-trigger).

plus two wording nits **[HOUSE-1]** / **[HOUSE-2]**. The decisions compose; the Q4 (direct, no wrapper)
vs Q5 (structure enforces the ref) pair is consistent once "enforces" is read as ref-enforcement, not
conformance-enforcement.
