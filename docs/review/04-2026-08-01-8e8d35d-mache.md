## A. Inconsistencies / contradictions

### A1. `FIX` — The gate timing for `authority=human` is stated three different ways
**Location:** `CONTEXT.md` L151 (Gating flow); `docs/adr/0006-autonomy-model.md` L26
(trigger-tier `reactive`); `docs/adr/0009-quality-gate-workflow.md` §7 (Delivery) + §8
(post-merge watchdog).

- **CONTEXT.md L151:** "_With `authority=human` the gate runs **post-merge** (reactive:
  human merges → gate review → fix PR if broken)._"
- **ADR-0006 L26:** trigger-tier `reactive` = "_(events: issue→work;
  **human-merge→post-merge gate review→fix PR**)_". (i.e. the post-merge review is framed
  as a reactive-tier event.)
- **ADR-0009 §7 (L91-93):** "_`authority=human` → dagmar opens the PR; Gate + Review run
  **pre-merge** as **advisory**; the human merges._ … The gate is **invariant** — it
  **always** runs on the candidate, **pre-merge** (ADR-0006)."
- **ADR-0009 §8 (L95-103):** the post-merge behavior is a **separate Workflow** (the
  watchdog) with a **filtered trigger** — "_not a component of every workflow_" — not
  "the gate running post-merge".

These do not agree. ADR-0009 (newest, most detailed) makes the gate **invariant
pre-merge** and carves the post-merge behavior into a **separate watchdog workflow**. But
CONTEXT.md L151 still says **the gate itself** runs post-merge for human authority, and
ADR-0006 L26 lists "post-merge gate review" as a reactive-tier event. Neither was updated
when ADR-0009 landed. Worse, ADR-0009 §7 cites **ADR-0006** as the source of "pre-merge" —
but ADR-0006 L26 actually says *post-merge*. So the citation is loose **and** the three
documents describe the same scenario three ways.

**Recommend:** reconcile all three to ADR-0009's model — (1) the gate is invariant and
always runs **pre-merge** on the candidate (advisory under `authority=human`); (2) the
post-merge review is a **separate watchdog workflow** with a filtered trigger, not "the
gate". Update CONTEXT.md L151 (and the ADR-0006 L26 reactive-tier parenthetical, or at
least ADR-0009's "(ADR-0006)" pointer) so a reader of any one doc gets the same timing.
Highest priority — this is the merge-safety flow described inconsistently across the
policy ADR, the workflow ADR, and the glossary.

## B. Undefined / under-defined terms

### B1. `GAP` — "Workflow" (CRD) is used throughout ADR-0009 but is absent from the glossary and the CRD boundary
**Location:** `docs/adr/0009-quality-gate-workflow.md` (L1, L17-19, L27, L63, L95-103,
L127); `CONTEXT.md` → CRD boundary + glossary (no entry).

ADR-0009 leans on "Workflow" as its **container concept** — "the Workflow concept is a
thin CRD that references a Dagger Go function … the quality-gate flow is **one workflow
family** within it" (§1), "a separate Workflow" (§8), "per-Workflow" (§4). But
`CONTEXT.md`'s CRD set is still `{Project, Agent, Prompt, QualityGate, Trigger, Run}` —
**no Workflow** — and the glossary has no Workflow entry. ADR-0009 §1/consequences defer
the general framework to seed `dagmar-ff60`, so Workflow is *referenced as established*
while being *undefined and unlisted*. Add at least a glossary stub (forthcoming CRD →
`dagmar-ff60`; today the quality-gate family is realized via `Run`/`QualityGate`/
`Trigger`).

### B2. `GAP` — `dagmar-bootstrap` / `dagmar-gate` Justfile targets are a new mandatory conformance contract whose relationship to the ProjectManifest is unspecified
**Location:** `docs/adr/0009-quality-gate-workflow.md` §2 (L35-36) + Consequences (L123-
124); cf. `docs/adr/0003-projectmanifest-in-repo-conformance.md` + `CONTEXT.md`
(ProjectManifest glossary).

ADR-0009 §2 makes Justfile targets `dagmar-bootstrap` (prepare workspace) and
`dagmar-gate` (run the checkables) a **required** project contract ("a Project must
expose … entry points (Justfile targets) as its gate conformance **alongside the
ProjectManifest**, ADR-0003"). Two issues:

1. **Overlap with ADR-0003 checkables.** The ProjectManifest already declares
   project-specific `checkables` (build/test/lint). `dagmar-gate` "run[s] the checkables".
   Is `dagmar-gate` the execution wrapper around the manifest-declared checkables
   (manifest = *what*, Justfile = *how to run*), or a parallel declaration? "Alongside"
   reads as separate, but then *which is authoritative for "the checkables"* is undefined
   — the exact projection ambiguity ADR-0003 was written to close.
2. **Undeclared hard dependency.** `just` (Justfile) is now a mandatory runtime tool for
   every conforming Project, mentioned **only** in ADR-0009 — not in ADR-0003 or the
   ProjectManifest glossary. This narrows the conformance surface silently.

**Recommend:** pin the relationship (manifest's `checkables` ← invoked by →
`dagmar-gate`; or fold the target names into the manifest) and record the Justfile
requirement as part of conformance.

### B3. `GAP` — "Sandbox trust-zone / hermetic-LLM network model" is referenced but has no ADR; ADR-0009's "hermetic via tool-set" rests on an undefined capability boundary
**Location:** `docs/adr/0009-quality-gate-workflow.md` §1 (L28), §3 (L43-49),
Consequences (L127-128); `CONTEXT.md` → Tool glossary; seed `dagmar-911b`.

ADR-0009 §3: "_The LLM agent loop runs hermetically — no network. This is enforced through
the **tool-set** … a hermetic agent's tool-set simply excludes any **network-capable
tool**._" But the CONTEXT.md `Tool` glossary defines the tool-set as "_`dag.git` /
`container` / `http` plus os-eco adapter exposures_" — and **`container` is
network-capable** (a process inside a container can reach the network), as can `git`
(remotes). So "excludes any network-capable tool" is **ambiguous**: is `container`
withheld for hermetic agents? Is `git`? The capability boundary is undefined, and the
full trust-zone model is deferred to seed `dagmar-911b` (no ADR yet). ADR-0009 thus asserts
hermeticity via a mechanism whose enforcement surface isn't pinned — security-relevant,
since the stated rationale is prompt-injection → exfiltration. See **C1**.

**Location:** `docs/adr/0009-quality-gate-workflow.md` §1, §3, Consequences ("sharpens

permits, and how "hermetic" is actually enforced (tool-set alone, or network policy on the
Sandbox pod, or both).

ADR exists, "Workflow" remains undefined (B1). Lower priority than C1 (the quality-gate
