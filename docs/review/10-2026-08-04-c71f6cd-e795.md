- **Scope:** `dagmar-e795` grilling output → ADR-0012 self-bootstrap trajectory

## Verdict

**Provisionally coherent — the trajectory shape is sound and the bootstrap boundary is the
right one, but do NOT flip to ACCEPTED until three things are revised in the ADR text:**

1. The **Phase 0 data path is incompletely bounded** — the agent-pod image + module ref are
   load-bearing for the bootstrap vertical itself and risk being swept into the deferred
   "full reconciliation semantics" bucket. ([GAP-1])
2. **§4's in-loop `quality_gate` reuse collides with ADR-0011 §2's hermeticity rule** in a way
   the ADR does not acknowledge. ([GAP-2])
3. **§4's "ADR-0009 §2 softens" misframes what §2 decides** — this is a conformance-mechanism
   *reassignment* (Justfile-wrapper → Dagger-harness), not a relaxation; the framing, the fate
   of `dagmar-bootstrap`, and the knock-on staleness in ADR-0011 must be made explicit. ([FIX-1])

The phase ordering (cognition-before-autonomy), the substrate choice (kind), the controller
fidelity (lean controller-runtime), and the dogfooding-is-structural stance all cohere cleanly
with ADR-0001…0011. The dispatch-vertical-without-LLM **is** the right boundary; what is missing
is a sharper statement of what Phase 0 must *read* to be provably complete.

## Findings (most severe first)

### [GAP-1] Phase 0 data path is incompletely bounded — agent-pod image + module ref are load-bearing and unspecified

**Where:** ADR-0012 §2, §3, §5 Consequences ("Deferred … the controller's full reconciliation
semantics").

The dispatch vertical says: reconcile a human-created `Run` → provision an agent pod
(SA + RBAC + cache-vol + `RUNNER_HOST=kube-pod://`) → the agent pod invokes the dagmar module
(`sandbox`/`probe-net`) → status back into the `Run`-CR. To do that the controller must resolve,
**before cognition**:

- **ProjectManifest / os-eco** — genuinely NOT needed in Phase 0 (`sandbox`/`probe-net` are
  engine/cache probes; ADR-0003 says the manifest is read "when it clones the repo for a
  Workspace"). ✅ safely deferrable.
- **Module source** — defined: the `Project` CR references repo+path (ADR-0003; the CR "has no
  `checkable-source` field; it reads checkables from the referenced manifest"). ✅ mechanism
  exists. **But** the *invocation target in Phase 0* is ambiguous: the agent pod invokes "the
  dagmar module" — on kind, is that a local-path ref, a published ref, or the dagmar-own
  Project's own module (which is the thing under development)? Not stated.
- **Agent-pod container image** — **UNSPECIFIED anywhere in ADR-0001…0012.** ADR-0002's `Agent`
  CRD carries definitions/policy (model/prompt/tool-set/checkable per CONTEXT.md's CRD→Tier-A
  bridge); ADR-0008 §2 specifies the *connection* (`kube-pod://` + SA + `pods/exec`) but not the
  *image*; ADR-0010 §2 says the agent pod "invokes the dagmar module" but not what image runs the
  `kube-pod://` Dagger client. The controller cannot `Create` a pod without an image ref.

**Why it matters:** image + module-ref resolution is the MVP itself, not "full reconciliation
semantics." §5 Consequences defers "dispatch concurrency, Workspace-lineage sequencing, webhook
admission, the controller's full reconciliation semantics" — a bucket broad enough to be read as
sweeping the MVP-necessary reads into the deferred seed. The ADR fixes *trajectory and fidelity*;
it must also fix the **Phase 0 read-surface** so the vertical is provably complete.

**Recommendation:** add a Phase-0 scope sentence: "Phase 0 controller reads the `Project` CR
(repo+path → module source) and a fixed agent-pod image (kind: controller-configured; real
cluster: image field to be decided in the control-plane seed). ProjectManifest/os-eco parsing is
deferred to Phase 2. Deferred: concurrency, lineage, admission, requeue/finalizer semantics."
State where the agent-pod image comes from even for kind (controller flag / ConfigMap / a future
`Agent`-CR field).

### [GAP-2] §4 in-loop `quality_gate` reuse collides with ADR-0011 §2 hermeticity

**Where:** ADR-0012 §4 ("reused … in-loop (coder self-verification)") + §5 Consequences ("Phase
1 … the checkable's build/test/lint run via container exec") vs ADR-0011 §2.

ADR-0011 §2 (ACCEPTED) withholds **the entire `container` tool** from hermetic agents (coder,
ReviewAgent) because `container.WithExec()` always has outbound network (ProbeNet) — "A hermetic
agent therefore cannot run local containers." ADR-0012 §4 makes `quality_gate` a container-exec
thing (build/test/lint) and reuses it **in-loop** for the coder. If the coder must wield the
`container` tool to self-verify, ADR-0011 forbids it.

The likely intended resolution (unstated): the checkable runs through the `CodeWorkspace`/Loop
harness (Tier-A machinery, `CodeWorkspace(source, checkable)`) — engine-side, not an LLM
`container` tool-call. **But that materially punctures ADR-0011's hermeticity claim**: the
hermetic coder would then have an *indirect* network-capable path (trigger quality_gate → engine
runs containers with network) — precisely what ADR-0011 §2's strong "cannot run local containers"
wording appears to preclude, and exactly the "tool-surface constraint, not network air-gap" caveat
(review N2) gestures at without resolving.

**Why it matters:** ADR-0012 leans on two ACCEPTED ADRs simultaneously (ADR-0011's hermeticity
and ADR-0009/CONTEXT.md's in-loop checkable) that are in tension once §4 sharpens quality_gate as
container-exec. Either (a) in-loop quality_gate for hermetic coders runs via the Workspace harness
→ ADR-0011 §2 needs an explicit carve-out ("except the checkable, executed by the Workspace
harness, not the agent's tool-set"), or (b) hermetic coders cannot self-verify in-loop → §4's
"reused in-loop" is wrong for the hermetic profile and contradicts ADR-0009 §3's two-profile
model.

**Recommendation:** §4 must state which path executes in-loop `quality_gate` for a hermetic coder
and reconcile that with ADR-0011 §2 (add the carve-out, or restrict in-loop reuse to the
non-hermetic profile). This is the sharpest contradiction the ADR introduces.

### [FIX-1] "ADR-0009 §2 softens" misframes a conformance-mechanism *reassignment*; `dagmar-bootstrap` and ADR-0011 left dangling

**Where:** ADR-0012 §4 consequence block (lines ~64-69) + Open-during-review (a).

ADR-0009 §2's actual model (verified, `0009-quality-gate-workflow.md` L36-46, L137-144):
manifest declares the checkables (the *what*) **and** the Project must expose
`dagmar-bootstrap` + `dagmar-gate` **Justfile targets** that *wrap* them (the *how to invoke*);
`just` is "a mandatory runtime tool for every conforming Project — a conformance dependency
introduced here." §2 already separates manifest (what) from wrapper (how) — it does **not** say
"conformance = expose a Justfile target" simpliciter.

ADR-0012 §4 says: "conformance = 'expose a checkable in the manifest,' not 'expose a Justfile
target'" and frames this as `just` "softening" from mandatory to "one option." Three problems:

1. **"Softening" is the wrong verb.** ADR-0012 *reassigns the mandatory-wrapper role* from
   `just dagmar-gate` (ADR-0009) to `dagger call quality_gate` ("Dagger is always the harness").
   The real invariant — there must be ONE deterministic entry point consuming manifest
   checkables — is *preserved* (good); the *language of the wrapper* changes (Justfile → Dagger).
   `just` is demoted from mandatory-wrapper to optional-body-transport; the conformance burden is
   not reduced, it is moved. "Softening" / the open-question framing ("vs. keeping `just`
   mandatory and layering `quality_gate` over it") understates that this **reverses the §2
   decision** and should *supersede*, not soften, ADR-0009 §2.
2. **`just` is not globally "one option."** If Dagger is always the harness, a Justfile-body
   project still needs `just` installed at runtime (the Dagger fn shells out to `just
   quality_gate`). The ADR conflates *conformance-interface* requirement (was: expose Justfile
   target — dropped) with *runtime* dependency (still present for Justfile-body projects).
3. **`dagmar-bootstrap` is silently dropped.** ADR-0009 §2 is a *two-stage* gate
   (`dagmar-bootstrap` prepare/install → `dagmar-gate` run), and ADR-0011 §2 names
   `dagmar-bootstrap` + `dagmar-gate` together as the non-hermetic, network-having profile.
   ADR-0012 §4 names only `quality_gate`. What happens to `dagmar-bootstrap` (dep install)?
   Folded into `quality_gate`? Kept as a separate Dagger fn? Unstated.
4. **ADR-0011 is left with stale references.** ADR-0011 §2's "(`dagmar-bootstrap`,
   `dagmar-gate`)" non-hermetic-profile naming becomes stale if `dagmar-gate` (Justfile) is
   retired. The §4 consequence note lists only ADR-0009 §2 + CONTEXT.md as acceptance-edit
   targets — **ADR-0011 should be listed too** (its non-hermetic-profile step names must track
   the rename).

**Recommendation:** reword the consequence to: *"ADR-0009 §2's conformance **mechanism** is
revised (supersedes, not softens): the mandatory deterministic wrapper moves from the Justfile
target `dagmar-gate` to the Dagger-harness entry `quality_gate`; the manifest remains the 'what.'
`just` ceases to be a conformance-*interface* requirement but remains a runtime dependency for
projects whose checkable body is a Justfile target. `dagmar-bootstrap` is folded into / kept
alongside `quality_gate` as ⟨stated choice⟩. Acceptance edits: ADR-0009 §2 + glossary/contract
lines, CONTEXT.md `checkable` glossary, **and ADR-0011 §2's non-hermetic step names**."*

### [SPEC-1] Phase 0 "status back into Run-CR" vs deferred "full reconciliation semantics" — bound the boundary

**Where:** ADR-0012 §2 + Open-during-review (c) vs §5 Consequences.

Open-question (c) asks to "confirm the dispatch-vertical reports status back into the Run-CR
(status conditions) as the first controller semantics, not just pod creation." **Yes — status
conditions are the right first semantics** (idiomatic K8s; the whole point of a `Run` CR per
ADR-0002 is "observable, reconciled execution … `kubectl get runs` supervises the autonomous
system"). But §5 Consequences defers "the controller's full reconciliation semantics," and
status-reporting *is* a reconciliation semantic — so the ADR is internally tense about where the
line sits.

**Recommendation:** confirm status conditions (phase + basic conditions: PodScheduled /
ModuleInvoked / Succeeded/Failed) are **in Phase 0 scope**; explicitly defer only the *heavier*
semantics (requeue/backoff policy, finalizers, conflict-retry, Workspace-lineage transitions).
State the boundary so (c) is closed, not just asked.

### [SPEC-2] Phase 2 bundling — sub-order within the bundle (answer to Open-during-review (b))

**Where:** ADR-0012 §5 (Phase 2 = Loop-wrapping + workspace/repo + os-eco adapters, bundled) +
Alternatives ("os-eco as its own phase … bundled into Phase 2 instead").

The chicken-and-egg argument for bundling os-eco with the coder-loop is valid (adapters are hard
to validate without a consuming loop). But bundling **three** major capabilities flatly is a
big-bang step that sits awkwardly with the ADR's own ethos ("prove the new part first … two
unbuilt things at once is rejected"). Loop-wrapping + workspace/repo do not depend on os-eco;
only the os-eco adapters need the loop as a consumer.

**Recommendation (answer to (b)):** keep the bundle but **sub-order within Phase 2** —
(2a) Loop-wrapping + workspace/repo model (cognition without os-eco; the coder self-verifies via
`quality_gate`), then (2b) os-eco adapter implementations (sd/ml/cn) consumed by the now-running
loop. This preserves the de-risking ethos while keeping the chicken-and-egg resolution.

### [HOUSE-1] `checkable` granularity shifts (plural → singular `quality_gate`)

ADR-0009 §2: *multiple* manifest checkables (build/test/lint) wrapped by `dagmar-gate`.
ADR-0012 §4: `quality_gate` is itself **the** (singular) checkable, reused in CI and in-loop.
CONTEXT.md Tier-A `checkable`: "mechanical self-verification (build/test/lint)." This is a real
model shift (a wrapper becomes a checkable; many become one). The promised CONTEXT.md "one-line
sharpening" (Dagger = harness; body flexible) does not capture the granularity change. Acceptance
should reconcile: is `quality_gate` the single umbrella checkable, or one-of-N checkables? State
it, else the `checkable` glossary and ADR-0009 §2's plural wording drift apart silently.

### [HOUSE-2] CRD types vs `.dagger/internal/domain/` — deliberate duplication, acknowledge it

ADR-0010 §1 argued a root "Dagger-free domain library" would be "artificial over-engineering,"
and §2 mandates **no Go-import coupling** between root controller and the `.dagger/` module.
ADR-0012 now puts `api/v1alpha1/{Project,Run,…}` in root, mirroring concepts that also live in
`.dagger/internal/domain/`. This is *correct* (different consumers: K8s API vs Dagger module;
decoupled by construction) but the consequence note implies a clean single model. Add one line:
the root CRD types and the `.dagger` domain core are intentionally parallel, not unified, per
ADR-0010 §1/§2's no-coupling rule.

### [HOUSE-3] In-cluster self-development recursion (latent risk, accept)

When Phase 2+ lands, the coder-loop edits dagmar-own source, which **includes the Phase 0
controller + CRDs** — the coder edits the control plane that runs it. "Deepest dogfood" flags
this warmly but does not name the risk: a coder change can break its own control plane. It is
adequately bounded by Phase 1 CI (`quality_gate` gates every change) + ADR-0006 (merge is a
deterministic controller function, two-green, merge tool in no Agent's tool-set) + the
human/auto merge-authority axis. No action; note it so the recursion is conscious, not accidental.

### [HOUSE-4] wayfinder `dagmar-80dd` menu coverage — #2 "partial" needs a completion home

§5 maps the 10 menu items to phases (P0→#2 partial; P1→#9; P2→#1/#3/#4; P3→#6/#7/#8;
Alongside→#5/#10). All 10 are covered, but #2 is "partial" in Phase 0 with no stated completion
phase. State where the rest of #2 lands (presumably Alongside/productionization or Phase 3), so
the menu ordering is provably exhaustive.

## Recommendation

**Revise-then-accept.** The trajectory, boundary, substrate, fidelity, and phase ordering are
coherent with ADR-0001…0011 and CONTEXT.md. Before flipping PROPOSED → ACCEPTED, address GAP-1
(Phase 0 read-surface), GAP-2 (hermeticity ↔ in-loop quality_gate), and FIX-1 (reword the §4
ADR-0009 consequence; account for `dagmar-bootstrap` + ADR-0011). SPEC-1/SPEC-2 close the ADR's
own open questions (c) and (b). The gated acceptance-edit (ADR-0009 §2 + CONTEXT.md) correctly
waits for acceptance — but its target list must add **ADR-0011 §2** (FIX-1.4), and the edit is a
*supersession*, not a softening.
