# Review 12 — dagmar Phase 0 controller scaffold

- **Commit:** `135944a` (HEAD, `feat(dagmar): Phase 0 controller scaffold`)
- **Baseline:** review 11 (`c332126`)
- **Scope:** Phase 0 control-plane scaffold — Increment 1 of ADR-0012. Seed `dagmar-67bc`
  is the design home for the deferred internals (requeue/backoff/finalizers/concurrency/
  webhook admission).
- **Reviewer:** dagmar-review (advice-only — no seeds filed, no fixes, no code/doc edits
  beyond this report).
- **Verdict:** **needs-fix-before-increment-2.** The scaffold is architecturally sound and
  standards-clean, but two coherence gaps stop the dispatch vertical from running end-to-end on
  kind as-is: `ModuleRef` is not wired into the `dagger call`, and the agent pod has no
  identity/RBAC to exec the singleton engine. Both are small, focused fixes — not rework.

## Findings

### 1. [SPEC] `ModuleRef` is a load-bearing Phase-0 read, but the reconciler never wires it into `dagger call`

ADR-0012 §2 (GAP-1) names two Phase-0 reads as **MVP-necessary, NOT deferred**: (1) agent-pod
image, (2) **module ref — "which dagmar module version the agent pod invokes"**. The scaffold
implements (1) — `agentPodFor` reads `project.Spec.AgentPodImage` and defaults to `alpine:3.20`
(`run_controller.go:132-135`). It does **not** implement (2): `project.Spec.ModuleRef` is defined
in `project_types.go:24-28`, rendered into the CRD schema, but **never referenced** anywhere in the
controller. The agent pod command is:

```
dagger call <ModuleFunction> <ModuleArgs>      // run_controller.go:137-140
```

with no `-m`/`--mod` flag, no `DAGGER_MODULE` env, and no module checked out (the pod image is a
fresh `alpine:3.20`). On such a pod `dagger call probe-net` cannot resolve a module → the call
fails at runtime. The dispatch vertical therefore cannot invoke the module end-to-end as coded.

**This is the headline gap.** Either:
- wire it: `dagger call -m <ModuleRef> <fn> <args>` (or set `DAGGER_MODULE=<ModuleRef>`), with a
  documented kind-vs-production resolution; or
- if ModuleRef's resolution mechanism is genuinely still open (the field doc says "deferred to the
  control-plane-design seed for the exact resolution mechanism"), then ADR-0012 §2's "module ref is
  load-bearing, IN scope, NOT deferred" is in tension with the field's own deferral note — the two
  should be reconciled, and the Phase-0 vertical needs *some* working module source (e.g. a baked
  default) until the ref is resolved.

**Needed before the Increment 2 kind proof.**

### 2. [GAP] Agent pod has no ServiceAccount / pods/exec RBAC to reach the engine — and the manager.yaml TODO mis-scopes it

ADR-0008 / ADR-0012 §2 specify the agent pod as *ServiceAccount + `pods/exec` RBAC + cache-vol +
`RUNNER_HOST=kube-pod://<engine>`*. The scaffold sets the runner host (`:136`, `:157`) but:
- the agent pod has **no `ServiceAccountName`** (`agentPodFor`, `:150-160`) → it runs as the
  namespace `default` SA;
- no Role/RoleBinding granting that SA `pods/exec` on the engine pod.

The engine lives in the **hardcoded** namespace `engineNamespace = "dagmar"` (`:24`), while the
agent pod is created in `run.Namespace` (the test uses `default`). The kube-pod:// runner performs
an exec into `kube-pod://<enginePod>?namespace=dagmar` — a **cross-namespace exec** from the agent
pod's own identity. That permission is missing.

`config/manager/manager.yaml` carries the TODO, but mis-scopes it:

> *"Local `just run` uses the kubeconfig user's perms, so this is only needed for in-cluster
> `just deploy`."*

This conflates the **controller's** identity with the **agent pod's** identity. Under `just run`,
the controller creates the agent pod using the kubeconfig user's perms — but the *agent pod itself*
then uses its **own** in-cluster ServiceAccount to exec the engine. The kubeconfig user's perms do
not transfer to the pod. So the agent pod needs `pods/exec` RBAC on namespace `dagmar` **even for
the `just run` kind proof**, not only for `just deploy`.

**Needed before the Increment 2 kind proof** (and the TODO note should be corrected). Likely shape:
a dedicated agent SA + a Role/RoleBinding (or ClusterRole) for `pods/exec` on the engine, scoped to
the engine namespace, plus a decision on whether Runs live in `dagmar` (same-namespace, simplest)
or arbitrary namespaces (ClusterRole).

### 3. [GAP] Transient missing Project or engine → Run sticks terminal `Failed` (no watch, no requeue)

`Reconcile` sets the Run to `RunPhaseFailed` and returns **nil** (no requeue) when the referenced
Project is absent (`:66-72`) or the engine pod is absent (`:75-79`). The controller watches only
`For(Run).Owns(Pod)` (`:214-219`) — it does **not** watch Projects or engine pods. Consequences:

- A Run created before its Project, or reconciled before the engine DaemonSet is ready, goes
  `Failed` and stays `Failed` even after the dependency appears — nothing re-enqueues it.
- `enginePodName` failing is not necessarily a permanent condition (engine still starting), yet it
  is recorded as a terminal phase.

ADR-0012 explicitly defers requeue/error-backoff/finalizers to the control-plane-design seed
(SPEC-1), so this is an *allowed* consequence — but for a kind proof driven by hand-applied YAML in
an unknown order, it is the most likely "why is my Run stuck Failed?" failure mode. At minimum,
returning an error (→ requeue with backoff) instead of a nil+terminal-Failed on a *transient*
missing-dependency would make Phase 0 self-healing without pulling in the full reconciliation
design. Flag for the Increment 2 proof; not a blocker if the proof sequences engine→Project→Run.

### 4. [HOUSE] `enginePodName` does a List every reconcile and picks `Items[0]` with no phase filter

`enginePodName` (`:94-104`) issues a labeled `List` on namespace `dagmar` on **every** reconcile and
returns `pods.Items[0].Name`. For a singleton engine at Phase-0 volume this is fine, but: (a) it is
one list call per reconcile forever (cheap to resolve once / cache); (b) the engine is deployed as
a helm **DaemonSet** (`name=dagger-dagger-helm-engine`) — on a multi-node kind cluster a DaemonSet
yields one pod per node, so `Items[0]` is nondeterministic, and there is no `status.phase=Running`
filter, so a Terminating/Failed engine pod could be selected. Phase-0-acceptable; note for scale.

### 5. [HOUSE] `setStatus` writes unconditionally (no diff)

`setStatus` (`:165-173`) always calls `Status().Update` every reconcile, even when phase and
condition are unchanged. `meta.SetStatusCondition` only bumps `lastTransitionTime` on a status
change, so the condition stays idempotent, but an API write still fires each reconcile → needless
resourceVersion churn. Minor; short-circuit when nothing changed.

### 6. [HOUSE] No sample CRs shipped — `config/samples/` is intentionally blank

The samples kustomization is left blank so kustomize does not fail. There is no shipped
`Project(dagmar-own)` + `Run` CR to drive the proof, and the README/Justfile has no recipe to apply
them. For a reproducible Increment 2 kind proof, a sample Project(dagmar-own) + a Run (or a
`just`/Dagger-function equivalent, per ADR-0009 §2) would remove hand-written YAML drift. Also: no
mechanism registers `dagmar-own` as a Project automatically — dogfooding step 1 is manual.

### 7. [HOUSE] `shellJoin` performs no escaping (acknowledged; revisit for Phase 2)

`shellJoin` (`:209-211`) joins `ModuleArgs` with single spaces and the whole command is passed to
`sh -c`. The comment (`:207-208`) explicitly accepts this for Phase 0 — the Run CR is a privileged
resource and args are author-controlled. Fine for the spike; flag for Phase 2, where ADR-0011
sandbox trust-zones will require safe arg passing for less-trusted inputs.

### 8. [HOUSE] Two package-level doc comments in `api/v1alpha1`

`doc.go` carries the package doc (`// Package v1alpha1 ...`); `groupversion_info.go` *also* carries
a comment immediately before `package v1alpha1` (`// SchemeBuilder registers ...`). Go concatenates
package comments across files, so this builds and vets clean — but the convention is to keep the
single authoritative package doc in `doc.go`. Cosmetic.

### 9. [HOUSE] Cache volume absent (acceptable for Phase 0; required for Phase 1)

ADR-0008 provisions a per-Project cache volume on the agent pod. The scaffold omits it. Phase 0
(probe-net/sandbox, no LLM) does not need cache isolation — the load-bearing Phase-0 reads are only
image + module ref (ADR-0012 §2) — so omission is defensible. Must land for Phase 1 (gate build/test
cache) / Phase 2. Noted for completeness.

### 10. [HOUSE] Agent pod requires network egress to install the dagger CLI

`curl -fsSL https://dl.dagger.io | sh` inside the agent pod needs outbound internet at runtime
(unless the CLI is baked into the image). On a kind cluster without a registry mirror / egress this
is an operational dependency. Not a code defect; flag for the proof environment.

## Recommended Increment 2 prerequisites (advice-only)

1. **Wire `ModuleRef`** into the agent-pod command (`dagger call -m <ref> …`) — or explicitly
   decide and document the Phase-0 module-resolution fallback (gap #1).
2. **Provision the agent-pod identity + `pods/exec` RBAC** for the engine namespace, and correct
   the manager.yaml TODO so it does not imply `just run` is exempt (gap #2).
3. Decide the **namespace topology** (Runs in `dagmar` vs arbitrary namespaces) — it determines
   Role vs ClusterRole for gap #2 and affects the cross-namespace exec design.
4. Consider a **requeue-on-transient-missing-dependency** (or a Project/engine watch) so the kind
   proof is not order-fragile (gap #3).
5. Ship a **sample `Project(dagmar-own)` + `Run`** (or a Dagger-function equivalent) so the proof is
   reproducible (gap #6).

None of these require architectural change — the scaffold's shape is right; it needs the two
load-bearing reads fully wired and the agent identity in place before the vertical can run.
