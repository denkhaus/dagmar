# Review — dagmar ADR-0011 (Sandbox trust-zones / hermetic LLM), second pass after pivot

**Date:** 2026-08-03 · **Commit under review:** `4206601` (PROPOSED) · **Scope:** `911b`
· **Prior pass:** `docs/review/07-2026-08-02-a1441a5-911b.md` (drove the pivot)
· **Role:** dagmar-review · **Mode:** advice-only (no seeds filed, no fixes applied)

The bell is dropped. ADR-0011 now decides: **one engine** (ADR-0008 unchanged, no re-open),
hermeticity of the LLM loop enforced via **per-use-case tailored tool-sets** (least privilege),
and the ProbeNet residual (a container exec has outbound network by default; v0.21.8 exposes
no per-exec no-network flag) **consciously accepted as a calculated risk**. This pass verifies
that the pivot resolves G1–G4, that the "calculated risk" framing is sound, answers the ADR's
own Open questions, and checks coherence + new gaps.

---

## Verdict

**The pivot is the right call and is largely successful.** G1–G4 evaporate cleanly (§ below),
the tool-set model dissolves the G3 tension with CONTEXT.md's "reused checkable" (the pivot's
single biggest coherence win), and the carryover housekeeping (review-07 F1/F2/H1–H4) is
cleanly retired. ProbeNet is now genuinely committed (`.dagger/main.go:269`) and the ADR no
longer overclaims "committed" — F1 is dead.

**However, the "calculated risk" framing over-claims completeness by under-scoping its threat
model.** §3 enumerates two exfiltration paths — the LLM-tool path (controlled) and the
raw-exec/checkable path (accepted) — and asserts the blast radius is bounded by ADR-0007.
That is all correct **for those two paths**. But the pivot silently removes a third control the
bell provided: against a **Dagger Sandbox-isolation break on the now-shared engine**, the bell's
deny-all-except-provider NetworkPolicy was a genuine compensating control (a break would land in
a network-isolated pod). With one unsegmented engine, that break's blast radius rests entirely
on Dagger's own Sandbox isolation — the very primitive that would have failed — plus K8s
namespace/RBAC. The acceptance is still *defensible* (Sandbox isolation is strong; probability
low), but it is **calculated only within a scoped threat model**, and the ADR never names that
scope. Naming it turns a hand-wave into a calculation; leaving it implicit is the one place the
"calculated" claim outruns its evidence (finding **N1**).

**Recommendation:** accept the pivot in principle; gate promotion on **N1** (name the
threat-model scope) + **N2/N3** (a "hermetic" gloss + the hermeticity criterion) + the
precision fixes **N4–N6** to §3/§4. These are clarification/spec edits, **not** architecture
rework — no re-open of ADR-0008, no bell resurrection.

## 1. Does the pivot resolve G1–G4?

**Yes — all four evaporate, exactly as the task predicted.** Confirmed each against the
rewritten ADR and the upstream ADRs:

- **G1 (hermetic base-image resolution) — RESOLVED.** The gap existed only because the
  hermetic bell's "deny-all-except-provider" NetworkPolicy blocked the registry pull the
  hermetic Sandbox/checkable needed (`dag.Container().From(...)` resolves engine-side as pod
  egress). With **one engine and no NetworkPolicy**, the engine reaches registries normally;
  there is no image-resolution split to close. The ADR correctly does not re-address it.

- **G2 (cross-engine Workspace-Directory handoff) — RESOLVED.** The gap was that bootstrap
  (networked) and coder (hermetic) were *different engine pods* with separate caches, so a
  `Directory` did not auto-transfer and the bell blocked the ADR-0004 shared-cache path. With
  **one singleton engine**, bootstrap → coder → gate → review all run on the same engine; a
  `Directory` stays in one engine's cache and crosses no trust-zone boundary. (Workspace-
  *lineage sequencing* remains deferred per ADR-0008 §5 / CONTEXT.md "Open questions" — but
  that is a control-plane concern, not G2's cross-engine dimension.)

- **G3 (in-loop-vs-gate checkable split vs CONTEXT.md "reused") — RESOLVED, and this is the
  pivot's key coherence win.** The bell forced the in-loop (hermetic engine) and gate
  (networked engine) instances of the *same* checkable into different network regimes, so a
  network-needing checkable could not be "reused" identically. In the tool-set model,
  hermeticity is a property of the **agent's `Env` tool-set**, not of the checkable's execution
  environment. The **same** checkable runs in-loop and at the gate; its raw-exec network access
  is identical in both. The difference is only the agent's Env. So "the checkable is reused in
  both" (CONTEXT.md `checkable` glossary, line 44) now holds without tension. (The checkable's
  network access is the *accepted residual* of §3 — correctly folded in, not re-appearing as a
  contradiction.)

- **G4 (DNS-exfiltration blind spot) — EVAPORATED.** G4 was a gap in a *sufficiency claim* —
  "deny-all-except-provider is sufficient" — because NetworkPolicy is L3/L4 and DNS tunneling
  stays open. The pivot makes **no** network-level sufficiency claim and imposes **no**
  NetworkPolicy; the tool-set is the control. So G4 is no longer a gap this ADR needs to close.
  The ADR explicitly accepts that the residual path can reach the network (§3), which is the
  honest position G4 was pushing toward.

**Carryover beyond G1–G4** (review 07): G5 (kube-pod control channel vs the egress policy) and
G6 (provider-allowlist granularity) are **retired** — there is no NetworkPolicy and no provider
allowlist to be granular about. F1 (ProbeNet "committed" but uncommitted) is **retired** —
`ProbeNet` is committed at `.dagger/main.go:269` and the ADR no longer says "committed". F2
(ADR-0009 §3 lead-sentence contradiction) is **retired** — ADR-0011 confirms the tool-set
mechanism (no bell re-open), so §3's assertion stands. H1 (stale "singleton"/"two engines"
statements) is **retired** — the Consequences explicitly notes "no 'two engines' wording to go
stale." H2/H3/H4 are **retired** (one engine; no §6 routing table under a bell; no
runtime-failing network tools under a bell). **H5 (shared-engine shared-fate blast radius)
carries forward and is *more* salient** — see N1. H6 (ProbeNet grounds the container-exec path
only) remains true and feeds N1.

## 2. Is the "calculated risk" framing sound?

**Sound within its stated threat model; the threat model is under-scoped (N1).** Decomposing
§3's three legs:

- **(a) Primary threat controlled — YES.** The threat is *the LLM primitive exfiltrating via
  its own tools* (prompt-injection → agent calls `http`/`git` to leak). Withholding those tools
  from the hermetic `Env` closes exactly that surface. This is the standard
  tool-surface-as-capability model, consistent with CONTEXT.md ("an Agent's permitted tools are
  its `tool-set` field"). Sound.

- **(b) Blast radius bounded by ADR-0007 — YES, with a precision fix (N4).** ADR-0007 genuinely
  provides: per-Project namespace (hard K8s credential boundary), per-`Run` projected-secret
  subset, and per-Project `llm` key (ADR-0007 §2 types `llm` as one of the three *per-Project*
  secret classes). So even the worst-case raw-exec exfil of the `llm` key is bounded to that
  Project — the bound holds. The precision issue (N4): §3(b) lists "the `llm` key never in any
  tool-set" as part of the *residual* bound, but the residual path is raw-exec, which does not
  go through the tool-set at all — so that line controls threat (a), not (b). Disentangling
  makes the argument tighter, not weaker.

- **(c) Residual path "deterministic / project-controlled / reviewed at the gate" — PARTIALLY
  (N5, N7).** The checkable *command* is fixed and manifest-declared (not arbitrary
  agent-authored shell) — true. But (N7) the *code under test* is agent-authored, and that code
  can make network calls (a `go test` / build step that curls out), so the residual surface is
  wider than "the fixed checkable command" implies. And (N5) "reviewed at the gate" is
  imprecise: the gate *runs* the checkable; it does not *inspect* it. The real control is human
  review at ProjectManifest declaration (ADR-0003). Neither breaks the acceptance — the surface
  is still bounded by (b) — but both should be stated accurately so "calculated" is not read as
  stronger than it is.

**The one place it tips toward hand-waved (N1):** §3's threat model implicitly scopes to two
paths — LLM-tool exfil and raw-exec exfil, both from a *single Sandbox*. It does not address a
**Dagger Sandbox-isolation break on the shared engine** (a Dagger CVE / container-escape). The
bell's deny-all-except-provider NetworkPolicy was a genuine compensating control for *that*
class: a Sandbox-isolation break would land in a network-isolated pod, unable to exfil except
to the provider, and unable to reach sibling Projects' pods. With one unsegmented engine, that
break's blast radius rests on (i) Dagger's own Sandbox isolation — the primitive that just
failed — and (ii) K8s namespace/RBAC/cache-volume naming (ADR-0007/0008). Defense-in-depth for
*credentials* still holds (namespace boundary), but the *network* blast radius on the shared
engine is uncontained in a way the bell would have contained. This is residual-on-the-residual,
probability is low, and the acceptance is defensible — **but the ADR must name this scope
explicitly** ("the threat model is LLM-tool + raw-exec exfiltration from a single Sandbox; a
Dagger Sandbox-isolation break is out of scope and was a property the rejected bell would have
improved"). Without that sentence, "calculated" claims a completeness the §3 enumeration does
not deliver. With it, the framing is honest and sound.

## 3. Answering the ADR's own "Open during review"

- **§3(b) — blast-radius-as-compensating-control framing.** *Right framing; tighten per N4.*
  Reliance on ADR-0007's bound is correct — it is a real, layered bound, and (crucially) the
  `llm` key is per-Project (ADR-0007 §2), so even raw-exec key-exfil is bounded. Two fixes:
  (1) move "the `llm` key never in any tool-set" to the primary-threat leg (a) — it is not part
  of the residual bound; (2) state explicitly that the `llm` key is per-Project, so the
  residual-path bound holds even in the worst case. That converts the bound from asserted to
  *traced*.

- **§3(c) — malicious Project declares a checkable that curls out.** *Accept as that Project's
  own compromise; the gate does NOT need to inspect checkable changes for exfiltration.* Two
  cases: (1) honest Project + prompt-injected agent — the checkable is benign, the residual is
  genuine, the bound is the acceptance; (2) malicious Project owner — they are exfiltrating
  *their own* projected secrets (their own `vcs`/`os-eco`/`llm` credentials), which is a
  non-threat: a Project can always leak its own creds, and dagmar's job is to bound it to that
  Project, which the namespace does. So no gate inspection of checkable *content* is required —
  the gate inspects checkables for **correctness** (does the change pass build/test/lint), not
  for security; security is the namespace boundary's job (ADR-0007). The fix (N5): reword
  "reviewed at the gate" → "human-reviewed at ProjectManifest declaration (ADR-0003); the gate
  executes, it does not inspect." State this decision so §3(c) is closed, not left open.

- **§4 / §2 — `container` egress vs the whole `container` tool.** *Withhold the whole
  `container` tool; "container egress" is not a real lever (N6).* `dag.Container().WithExec()`
  always has outbound network (ProbeNet) — there is no tool-set flag that withholds "egress"
  while keeping the `container` tool for local builds. That is exactly the per-exec-no-network
  capability v0.21.8 lacks. So the cut collapses to: either (a) the hermetic `Env` has **no**
  `container` tool (the LLM cannot directly build/run containers; only the manifest-declared
  checkable does, controller-invoked) — the clean choice; or (b) the hermetic `Env` *does*
  carry `container`, in which case that use reintroduces a raw-exec network path and must be
  folded into §3's residual rather than listed under "withheld." Note the **asymmetry** the
  current wording hides: `http` and `git` are cleanly withholdable as *whole* tools (`dag.git`
  *is* the remote-clone capability), but `container` is not sub-dividable. Pick (a), and replace
  "`container` egress" with "the `container` tool" in §2/§4.

## 4. Coherence vs ADR-0004 / 0007 / 0008 / 0009 + CONTEXT.md

- **ADR-0008 — coherent.** §1 ("ADR-0008 unchanged, no re-open") is accurate: singleton engine,
  no trust-zone split. Consequences correctly retires H1.
- **ADR-0007 — coherent.** §3(b) faithfully cites ADR-0007's defense-in-depth (verified: per-
  Project namespace, per-`Run` projection, `llm` key per-Project and never in a tool-set). No
  weakening.
- **ADR-0009 §3 — mechanism coherent; wording drift (N8).** ADR-0009 §3 asserts hermeticity
  "via the tool-set" and defers the per-tool boundary here — ADR-0011 §4 delivers exactly that,
  so the forward-pointer lands cleanly and F2 is dead. *But* ADR-0009 §3's plain words "runs
  **hermetically — no network**" are now softer than literal: the checkable's raw-exec path has
  network. ADR-0011 claims "ADR-0009 §3: resolved" without flagging that the *wording* "no
  network" is now imprecise (the *Env* has no network tool; the *Sandbox* is not air-gapped).
  Either amend ADR-0009 §3 to "no network-capable tool on the `Env`" or note the drift.
- **CONTEXT.md "reused checkable" — coherent now (the pivot's win).** With G3 dissolved, the
  `checkable` glossary ("reused both in-loop … and as the mechanical layer of the QualityGate",
  line 44) sits cleanly: one checkable, identical raw-exec behavior in both places, hermeticity
  expressed only via the agent `Env`. No change to CONTEXT.md needed (correctly noted in
  Consequences). The `Tool` glossary ("an Agent's permitted tools are its `tool-set` field",
  line 51) is consistent.

## 5. New gaps the pivot introduces

- **[GAP] N1 (medium-high) — threat model under-scoped; "calculated" over-claims completeness.**
  See §2. The bell's deny-all-except-provider NetworkPolicy was a compensating control against
  a **Dagger Sandbox-isolation break on the shared engine**; the pivot removes it and rests
  that class entirely on Dagger's own Sandbox isolation + K8s namespace/RBAC. Name the scope
  explicitly ("threat model = LLM-tool + raw-exec exfil from a single Sandbox; Sandbox-
  isolation-break out of scope; the rejected bell would have helped there"). This is the single
  fix that converts the framing from asserted to calculated.
- **[GAP] N2 (medium) — "hermetic" is now overloaded / softer; reader-over-trust risk.**
  ADR-0009 §3 and CONTEXT.md (line 33 "the hermetic Dagger execution engine", line 215 "hermetic
  LLM via tool-set") say "hermetic / no network," but ADR-0011's tool-set hermeticity still
  permits the checkable's raw-exec network. Add a one-line gloss: *hermetic = the `Env`
  tool-surface excludes network-capable tools; it is not a Sandbox network air-gap*.
- **[GAP] N3 (medium) — hermeticity CRITERION unstated.** The ADR states the *mechanism*
  (tool-set) but not *which agents are hermetic*. The threat model (seed 911b: "LLM processes
  untrusted content → highest isolation") implies **all LLM agent loops** (coder, reviewer) are
  hermetic and **deterministic infra** (bootstrap, gate) is not. §2 says "a hermetic agent's
  Env …" without pinning the agent/infra split. State the criterion: hermeticity applies to
  Agent Loops that process untrusted content; bootstrap/gate retain network. (Currently
  deferred to per-Agent `tool-set` values — fine to defer the *sets*, not the *principle*.)
- **[GAP] N7 (low-medium) — §3(c) residual surface understated.** "Not arbitrary agent-authored
  shell" is true for the checkable *command*, but the *code under test* is agent-authored and
  can make network calls (a test/build that curls out). Still bounded by §3(b); state the wider
  surface so it is not under-estimated.
- **[HOUSE] N9 — the bootstrap→LLM→gate flow is not re-stated.** Seed 911b asked to "define …
  the bootstrap->LLM->gate flow." The bell draft's §7 did (with the cross-engine handoff); the
  pivot makes it trivial (one engine, in-engine data passing, no handoff) but does not say so.
  One sentence closes it.
- **[HOUSE] N10 — seed 911b title drift.** The seed *title* says "network segmentation"; the
  decision is tool-set *capability* segmentation (no network segmentation). The seed
  *description* ("enforced via the Agent tool-set … deterministic infrastructure has network")
  matches the ADR, so this is title-only staleness. (Advice-only — not filing seeds.)
