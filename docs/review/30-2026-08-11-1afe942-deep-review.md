## Executive Summary

The codebase is architecturally coherent — 27 ADRs, a well-structured hexagonal Go layout, a
working controller-runtime reconciler with FSM-driven orchestration, and a deterministic Dagger
gate. However, **the gate itself is currently RED on its own codebase**: 9 files fail `gofmt`,
which the controller checkable enforces. The latest commit (ADR-0026 FSM) left ~680 lines of
dead code from the superseded `advance*` functions, and ADR-0027 (CognitionRun pipeline) has
already superseded ADR-0026 but is not yet implemented — the code is in a transitional state
between two superseded designs. Cross-module dedup (manifest module) is incomplete: `GateResult`,
meta-prompts, and tools.go are duplicated or stale. The gate's fail-open evaluation and missing
`-race`/golangci-lint/govulncheck coverage are the highest-risk gaps.

### [RISK] A5 — Ignored status-patch errors
`patchStatus` return values are ignored in 8+ call sites (`_ = r.patchStatus(...)`). The

### [HOUSE] A6 — Duplicate phase constants
Two parallel sets define the same string values:
- `pipeline_fsm.go`: `StateCoding = "coding"` … `StateDone = "done"`
- `orchestration.go`: `PipelineCoding = "coding"` … `PipelineDone = "done"`

The FSM path uses `State*`; `transitionPipeline` (which the FSM calls) checks `Pipeline*`.
They happen to match by string value, but this is fragile — a rename in one set breaks the
other silently.

### [RISK] A7 — `parseDagmarExit` takes LAST match (prompt-injection adjacent)

the LAST match. If a checkable's stdout contains `DAGMAR_EXIT=0`, the gate reports success
even if the command failed. Low risk for current checkables (go build/vet/test don't emit
this), but a pattern vulnerability for future checkables or adversarial output.

## E. Dagmar-Gate Deep Analysis

### E1. Completeness

**[FIX] E1a — Gate is RED on its own codebase (gofmt violations).**
The controller checkable runs `test -z "$(gofmt -l .)"`. Currently 9 files fail gofmt:
`.dagger/internal/app/output.go`, `.dagger/internal/app/review.go`,
`.dagmar/internal/workflows/gate.go`, `.dagmar/internal/workflows/hooks.go`,
`internal/controller/orchestration_fsm.go`, `internal/controller/orchestration_test.go`,
`internal/controller/pipeline_fsm.go`, `internal/controller/run_controller.go`,
`internal/controller/run_controller_test.go`. The violations are cosmetic (trailing whitespace,
blank lines, import ordering, struct alignment, missing trailing newline) but the gate
enforces them. **The code was committed without passing its own gate.**

**[GAP] E1b — No `go test -race` in the gate.**
The gate runs `go test ./...` without `-race`. The controller's reconcile loops, status
patches, and Sub-Run watches involve concurrent access patterns. A data race would pass the
gate. `-race` is affordable for the current test suite (4.6s with -race on root).

**[GAP] E1c — No golangci-lint in the gate.**
golangci-lint v2.12.2 is installed via mise.toml but the gate does NOT run it. The gate
relies on `go vet` only. golangci-lint found 12 issues (6 unused, 5 SA1019, 1 QF1003) that
`go vet` does not catch. The gate should run `golangci-lint run` as a checkable — or at least
document why it's deliberately omitted.

**[GAP] E1d — No `go mod tidy` consistency check.**
`manifest/go.mod` carries an unused `require gopkg.in/yaml.v3 v3.0.1`. `.dagmar/go.mod` has
a stale indirect `yaml.v3` + a stale `manifest v0.1.0` hash in go.sum. `go mod tidy -diff`
would catch these. The gate doesn't verify tidy consistency, so a committed go.sum that
doesn't match go.mod would pass.

**[GAP] E1e — No govulncheck / dependency vulnerability scanning.**
Known CVEs in Go dependencies would pass the gate undetected.

**[GAP] E1f — No CRD schema / DeepCopy generation verification.**
The gate does not verify that `config/crd/bases/` is up-to-date with `api/v1alpha1/` +kubebuilder
markers, nor that `zz_generated.deepcopy.go` is current. (No `config/crd/bases/` or
`zz_generated.deepcopy.go` exist yet — they need controller-gen — but once added, drift is a
common K8s-controller bug.)

**[INFO] E1g — Other file types unvalidated.**
The gate runs Go checks only. mise.toml, .gitignore, YAML configs (if any future CRD samples
exist), and lefthook config are not validated by the gate.

### E2. Strictness

**[RISK] E2a — Fail-OPEN gate evaluation (CRITICAL DESIGN FLAW).**
In `evaluateGate` (orchestration_fsm.go L256): `gateGreen := true`. If `readGateResult` fails
(pod not terminated, no termination message, JSON parse error), `gateGreen` stays `true` and
the pipeline assumes the gate passed. This is fail-open: a broken gate result → automatic
green. Documented as "ADR-0020 D3 stub behavior" but this is a safety-critical invariant — the
QualityGate is described in CONTEXT.md as "always secures quality." **Recommendation:** default
to `gateGreen = false` (fail-closed) and only set green when a valid GateResult confirms it.
A transient pod-not-terminated state should requeue, not assume green.

**[INFO] E2b — Fail-fast gate (returns on first failure).**
`Gate()` in gate.go returns immediately on the first failed checkable (L57: `return
marshalGate(result)`). The agent revise loop gets feedback for ONE check at a time. A
run-all-and-report approach would give the agent more per-round feedback (e.g., both
gofmt violations AND a test failure in one gate result).

**[INFO] E2c — Coverage floor defaults to 0 (disabled).**
`coverageFloorBps` defaults to 0 on the `DagmarGate` function. If the caller forgets to pass
it (or the Project's CoveragePolicy is not enabled), coverage is never checked. This is by
design (opt-in) but means the coverage ratchet is inert unless explicitly configured.

**[INFO] E2d — Secret scan scans everything.**
`betterleaks dir .` scans the entire tree including generated files (dagger.gen.go,
zz_generated) and .git/. No exclusions configured. False positives from generated files would
be noisy. (Currently passes — no false positives found — but scaling risk.)

**[RISK] E2e — MaxReviseRounds default = 3.**
`maxReviseRoundsFor` returns 3 when unset. For complex tasks, 3 coder→gate→revise cycles may
be insufficient. This IS per-Workflow (via QualityGateRef.MaxReviseRounds) but the default
is hardcoded in the controller, not a CRD default. The CRD field has `+kubebuilder:default=3`
but `maxReviseRoundsFor` falls back to a literal `3`, not the CRD default.

### E3. Contract Robustness

**[RISK] E3a — `parseDagmarExit` takes LAST match.**
See A7. If output contains multiple `DAGMAR_EXIT=` lines (e.g., a compiler error message
referencing an env var), the last one wins. Should take the FIRST match (the `echo` is
appended after the command) or use a unique sentinel.

**[INFO] E3b — `marshalGate` fallback IS untested.**
`marshalGate` (gate.go L82) has a fallback for `json.Marshal` failure returning a hardcoded
JSON string. Since the struct is simple (bool + slice + ints), marshal failure is near-
impossible. But the fallback is dead-untested code with zero coverage.

**[INFO] E3c — Truncation at 2000 chars may lose diagnostics.**
`truncateForTerminationLog` caps at 2000 chars. For a failing `go test` with verbose output,
the useful error may be truncated. ADR-0025 / ADR-0027 address this by moving outputs to
Dagger function return values (no termination-log limit), but the current code still relies
on truncation.

**[INFO] E3d — Gate never returns a Go error.**
`Gate()` returns `(string, error)` but the error path is always `marshalGate(result)` with
`{"passed": false}` — the error return is never used for failure signalling. The error
return is vestigial; callers must parse the JSON. This is by design (ADR-0009 S2: deterministic
JSON contract) but the `(string, error)` signature is misleading — it suggests error-based
failure handling.

**[PASS] E4b — ADR-0017 S3 (checkables are Go code):** `gateChecks` is a Go slice of

**[PASS] E4c — ADR-0014 (module boundary):** `.dagmar` is separate from `.dagger`. ✓

## F. Gaps, Stubs & Misconceptions

### [FIX] F1 — Dead code from pre-FSM era (see A1)
The four `advance*` functions + two unused helpers represent ~680 lines of dead code that
implement the OLD orchestration logic (including the same fail-open gate evaluation, duplicated

### [GAP] F2 — Gate evaluation is a stub (fail-open)
`evaluateGate` and `evaluateReview` both use Phase-2 interim stubs:
- `evaluateGate`: assumes green if gate result unavailable (E2a).
- `evaluateReview` (orchestration_fsm.go L272): `return sub.Status.Phase == v1alpha1.RunPhaseSucceeded`
  — success = approve. The full reviewer JSON verdict parsing is not wired (tracked in
  seed `dagmar-be2c`, resolved/closed per ADR-0027 but not implemented in this codebase).

### [GAP] F3 — Shell-injection vector documented but unfixed
`agentPodFor` (run_controller.go L350–354) interpolates unescaped `ModuleRef`,
`ModuleFunction`, and `ModuleArgs` into a `sh -c` command string. Documented as Phase-0-safe
(author-controlled) but a "LIVE injection vector for agent-generated Runs (Phase 2)."
Tracked in seed `dagmar-326f`.

### [GAP] F4 — Stale `yaml.v3` dependency
`manifest/go.mod` requires `gopkg.in/yaml.v3 v3.0.1` — a leftover from the YAML manifest era
(ADR-0017 removed the manifest YAML). `go mod tidy` would remove it. The `.dagmar/go.mod`
also carries it as indirect + a stale `manifest v0.1.0` sum hash.

### [HOUSE] F5 — `mise.toml` comment is stale
mise.toml L2: "the root module declares 1.26.1" — but root `go.mod` now declares `go 1.26.5`.
All four modules are aligned at 1.26.5; the comment is outdated.
