## A. Standards

### A1. [FIX] CONTEXT.md "CRD boundary" section contradicts the glossary (CRITICAL)

`CONTEXT.md` → `## CRD boundary` (bottom of file). The glossary header at L72 was correctly
updated: "`CRD set` (ADR-0002, extended by ADR-0016): `{Project, Agent, Prompt, QualityGate,
Trigger, Workflow, Run}`." But the "CRD boundary" section below was **not** updated and still
reads:

> CRDs: `{Project, Agent, Prompt, QualityGate, Trigger, Run}`. Non-CR: `{Task, Sandbox,
> Workspace, ProjectManifest}`. **Workflow** is referenced by ADR-0009 but is *forthcoming*,
> not yet a CRD (→ seed `dagmar-ff60`).

This directly contradicts the glossary 50 lines above it and ADR-0016 §7. The diff edited the
glossary section but missed this section. **Fix:** update the CRD set to include `Workflow` and
remove the "forthcoming, not yet a CRD" clause.

### A2. [HOUSE] Workflow glossary entry placed under wrong section heading

`CONTEXT.md` L126. The Workflow (CRD) entry was moved out of the deleted "Forthcoming" section
but landed immediately after `ProjectManifest`, which sits under the
**"In-repo manifest (not a CRD):"** header (L113). A CRD listed beneath a "not a CRD" heading is
structurally misplaced. **Fix:** move the Workflow entry up into the CRD glossary block (e.g.,
between `Trigger` and `Run`, matching the CRD-set order).

### A3. [FIX] Run glossary entry and "Execution quartet" not updated for dual-mode

`CONTEXT.md`, Run entry + Key relationships. ADR-0016 §2 introduces **dual-mode Run**
(atomic/orchestration). The glossary still defines Run as "one execution of an Agent, in one
Sandbox, on one Workspace" — an orchestration Run has no Agent/Sandbox/Workspace of its own; it
supervises Sub-Runs. The "Execution quartet" relationship ("a Run is the product of
`{Agent, Sandbox, Workspace}`") similarly fails for orchestration Runs. **Fix:** qualify the Run
definition ("atomic Run = {Agent, Sandbox, Workspace}; orchestration Run supervises N atomic
Sub-Runs per ADR-0016 §2") and note the quartet applies to atomic Runs / Sub-Runs.

### A4. [FIX] German word in English ADR text

`ADR-0016` §8, line "The QualityGate CRD defines *what* the gate checks (checkables, rules,
thresholds) — **deklarative** policy." "deklarative" is German; should be "declarative" in a
persisted English document. One-word typo, trivial fix.

## C. Inconsistencies / contradictions

### C1. [FIX] = A1 (CRD boundary section). See above.

### C2. [GAP] Trigger flow model unreconciled between CONTEXT.md and ADR-0016

`CONTEXT.md` → "Trigger flow": `Trigger → seeds issue → Task → Run(s)`.
`ADR-0016` §6: "When the event fires, the controller creates an orchestration Run
(`spec.workflowRef` set)."

The ADR introduces Trigger → orchestration Run directly but does not reconcile with the
Task-mediated flow in CONTEXT.md / ADR-0013 §3 (where lineage is tracked per-Task via
`spec.taskRef`). Open questions: Does the orchestration Run still carry a `taskRef`? Does the
Trigger still create a Task (seeds issue) first, or does it create the Run directly? §9 defers
Trigger *implementation* to Phase 3, but the **design-level flow** should be pinned now.

### C3. [GAP] RunSpec Go struct missing `parentRun` and `taskRef`

ADR-0016 §2 references a `parentRun` reference on Sub-Runs ("Sub-Runs carry `ModuleFunction`
…and a `parentRun` reference linking them to their orchestration Run") but the Go struct shown
(`RunSpec`, §2) has no `parentRun` field. Separately, ADR-0013 §3 relies on `spec.taskRef` for
per-Task lineage tracking, but the RunSpec struct in ADR-0016 omits `taskRef` as well. The shown
struct is incomplete relative to the text's own references. *(Noting: these ADR-level structs are
illustrative, not committed Go code; but a reader implementing from the ADR will miss the field.)*

## D. Undefined / under-defined terms

### D1. [GAP] "calibration" PipelinePhase vs. deferred Calibration Agent

ADR-0016 §3 lists PipelinePhase values: `"gate" | "coder" | "review" | "calibration" | "done"`.
But ADR-0006 defers the Calibration Agent (operator-approved initially). The ADR does not clarify
whether the "calibration" phase is reachable in Phase 2 (before the Calibration Agent is
implemented) or only activates when that agent exists. Recommend noting this as a Phase-2-later
phase.

### D2. [GAP] Max-revise-rounds escalation has no corresponding PipelinePhase

ADR-0009 §4: "max N rounds (default 3, per-Workflow) → escalate to a human." ADR-0016 §1 carries
`maxReviseRounds` (default 3) but the PipelinePhase values have no "escalated" / "human-review"
terminal state. What PipelinePhase does the controller write when `maxReviseRounds` is
exhausted? Either add a phase (e.g., `"escalated"`) or clarify that "done" subsumes it with a
status condition.
