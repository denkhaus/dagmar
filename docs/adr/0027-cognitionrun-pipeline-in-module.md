# ADR-0027: CognitionRun pipeline — step orchestration in the Dagger module (greetings-api pattern)

- **Status:** decided
- **Date:** 2026-08-11
- **Evidence:** resolves dagmar-be2c/d8dc/16fb/3c07 (all closed); supersedes ADR-0026 D2/D3/D5
  (step-level FSM topology); revises ADR-0025 (termination-log removed entirely); revises
  ADR-0016 §4, ADR-0021 D3, ADR-0023 D3/D5, ADR-0024 D4. Reference: greetings-api
  (github.com/kpenfound/greetings-api, mulch mx-e05f90) — DevelopPullRequest chains
  Develop→PullRequestReview as Go-method calls within one Dagger module function.
- **Decided in:** grilling session 2026-08-11 (12 questions, all settled).

## Context

The orchestration controller (ADR-0026 FSM) orchestrated each pipeline step as a separate
K8s Sub-Run + agent pod. Each Sub-Run called `dagger call` via a shell-interpolated command,
and results propagated via `/dev/termination-log` (2048-byte limit, truncated output).

This has three structural problems:

1. **Result propagation is broken:** termination-log truncates; shell chaining is fragile;
   reviewer verdicts and gate results lose data in transit.
2. **Revise loops are expensive:** gate-red → new Sub-Run → new pod → new Prompter Loop (20+
   API calls) → new Coder Loop. The agent has no memory of prior failed attempts.
3. **The controller does work Dagger should do:** step sequencing (prompt→code→gate→review)
   is pure function chaining — no K8s state, no policy decisions. It belongs in the Dagger
   module, not the controller (greetings-api pattern).

## Decision

### D1 — CognitionRun is a Dagger custom object with exported state fields

The pipeline is a Dagger custom object (`CognitionRun`) with exported struct fields that
Dagger serializes between function calls in a chain (Dagger Go SDK: *"Exported struct fields
are part of the object's state and are serialized between functions in a chain"*).

The pipeline chains the existing app-layer functions (`Prompt`, `Code`, `Gate`, `Review`,
`Adjudicate`) as Go-method calls. Results flow as Go types (`*dagger.Directory`, `ReviewVerdict`,
`string`) — no termination-log, no shell interpolation, no Sub-Runs.

```go
// CognitionRun is the pipeline as a Dagger custom object.
type CognitionRun struct {
    Source        *dagger.Directory
    TaskContext   string
    Model         string
    MaxAPICalls   int
    GateRef       string         // project module ref for gate (Container.WithExec)
    CallbackURL   string         // controller endpoint for Collector pushes
    CallbackToken string         // Bearer token for auth
    MaxRevise     int            // revise-loop limit (policy from QualityGate)
}
```

The CLI invocation is a single call: `dagger call cognition-run --source . --task-context "..."`.

### D2 — Internal revise loops preserve LLM context

Revise loops (gate-red → re-code) happen INSIDE the pipeline, not as controller-dispatched
retries. The coder's LLM context is preserved across revise attempts — the agent remembers
prior failures and adjusts (same pattern as greetings-api's `DevelopFeedback`, which feeds
prior work + feedback into the same agent loop).

`maxRevise` is passed as a pipeline parameter (from the QualityGate CRD). When exhausted,
the pipeline returns `{outcome: "max_retries_reached"}` — the controller decides escalation.

### D3 — Collector: deterministic step-result push to controller

After each pipeline step, a Collector function pushes the accumulated state as JSON to the
controller's HTTP endpoint (`--callback-url`). The Collector is:

- **Unidirectional** — push only, no mid-pipeline intervention from the controller.
- **Deterministic** — pure data serialization, no LLM, no decisions.
- **Optional** — when `--callback-url` is empty, the pipeline runs without Collector pushes
  (testable without a controller).

The controller stores received step results in `Run.Status.StepResults` (new CRD field).
This gives the FSM fine-grained visibility into what happened during the pipeline run.

Auth: per-run Bearer token (`--callback-token`), generated by the controller at dispatch time.

### D4 — Gate via Container.WithExec (not CLI shell interpolation)

The gate runs via `dag.Container().WithExec([]string{"dagger", "call", "-m", gateRef,
"dagmar-gate", "--source", ...})` — a Go-level call, not shell-interpolated `sh -c`. The
result (GateResult JSON) is a Go return value, not termination-log output.

### D5 — FSM simplified to policy level

The FSM (looplab/fsm, ADR-0026 D1/D4 retained) transitions from step-level to policy-level:

```
dispatching → running → done
                ↓
            escalated
```

The controller evaluates the pipeline's final JSON result:
- `outcome=approve` → done
- `outcome=max_retries_reached` or `outcome=error` → escalated
- Step-level details (gate results, review verdicts) available via `Run.Status.StepResults`

Step-level states (coding/gating/reviewing/adjudicating) are internal to the CognitionRun
pipeline, not exposed as Run status.

### D6 — Result propagation: ConfigMap at pipeline completion

When the pipeline completes, the pod exports the final JSON via `dagger call -o /tmp/result.json
cognition-run ...` and writes it to a ConfigMap:

```bash
dagger call -o /tmp/result.json cognition-run ... && \
kubectl create configmap dagmar-result-<run> --from-file=result=/tmp/result.json
```

The controller reads the ConfigMap at pod completion. No termination-log, no size limit.

## Consequences

- **termination-log is removed entirely** — including for the deterministic gate. ADR-0025's
  exception for the gate is revoked.
- **Sub-Runs are removed** — the controller dispatches one pipeline call per Run, not N Sub-Runs.
  `getOrCreateSubRun`, `subRunConfigForState`, and the `advance*` functions are deleted.
- **The FSM retains looplab/fsm** but with policy-level states (3-4 instead of 6).
- **Revise loops are cheaper** — the agent keeps its LLM context, only re-running the code
  Loop (not the Prompter Loop).
- **`/dev/termination-log` references** are removed from run_controller.go, orchestration.go,
  orchestration_fsm.go, and .dagmar/internal/workflows/gate.go.
- **New CRD field:** `Run.Status.StepResults []StepResult` for Collector-pushed data.
- **New controller endpoint:** HTTP server (Runnable) on port 8082, `POST /step-result`.
- **Gate cross-module call:** the pipeline calls the project's gate via Container.WithExec,
  using the `GateRef` (module source ref) parameter. The platform module does not compile in
  any specific project's gate.
